Module 01 · Getting Started

Introduction & Why Kubernetes

What container orchestration solves, how Kubernetes emerged from Google's internal Borg system, and the core ideas — declarative desired state, reconciliation loops, and self-healing — that every other module builds on.

A. The problem before Kubernetes

Docker made it easy to package an app into a portable container. But running containers in production raises questions Docker alone doesn't answer: Which host runs which container? What happens when a host dies? How do containers find each other? How do you roll out a new version without downtime? How do you scale from 3 replicas to 300?

Kubernetes (often abbreviated K8s — "K", 8 letters, "s") is a system that answers all of these by treating a group of machines as a single pool of compute, and letting you describe what you want rather than scripting how to do it.

Origin. Kubernetes was open-sourced by Google in 2014, distilling a decade of lessons from Borg and Omega, Google's internal cluster managers. It's Greek for "helmsman" — the person who steers a ship, which is also why the logo is a ship's wheel.

B. Declarative vs imperative

Imperative

"Start 3 containers on host A, 2 on host B. If one crashes, SSH in and restart it." You script every step and every failure case yourself.

Declarative (Kubernetes)

"I want 5 replicas of this container running, always." You write the desired state as YAML; Kubernetes continuously works to make reality match it.

C. The reconciliation loop (the single most important idea)

Every Kubernetes controller runs the same loop, forever:

observe current state  →  compare to desired state  →  take action to close the gap  →  repeat

This is why Kubernetes is self-healing: if a Pod dies, the gap between "3 desired" and "2 actual" is detected within seconds, and a new Pod is scheduled automatically — no human, no script, no alert-and-respond.

D. What Kubernetes gives you

  • Scheduling — decides which node runs which workload based on resource needs and constraints.
  • Self-healing — restarts failed containers, reschedules Pods from dead nodes, kills containers that fail health checks.
  • Horizontal scaling — scale replicas up/down manually or automatically based on CPU/memory/custom metrics.
  • Service discovery & load balancing — Pods get a stable DNS name and traffic is spread across healthy replicas.
  • Automated rollouts & rollbacks — change the desired state and Kubernetes migrates traffic gradually, and can roll back instantly on failure.
  • Secret & config management — inject credentials and configuration without rebuilding images.
  • Storage orchestration — automatically mount local, cloud, or network storage.

E. What Kubernetes is not

Not a PaaS. Kubernetes doesn't build your code, doesn't provide a database service out of the box, and doesn't dictate CI/CD, logging, or monitoring tooling — it's a foundation that those tools plug into (Helm, Prometheus, ArgoCD, Istio, etc. all sit on top of it).

F. The vocabulary you'll use constantly

TermMeaning
clusterA set of machines (nodes) running Kubernetes, managed as one unit.
nodeA single machine (VM or bare metal) in the cluster.
PodThe smallest deployable unit — one or more tightly-coupled containers.
manifestA YAML/JSON file describing desired state of a Kubernetes object.
kubectlThe CLI used to talk to a cluster's API server.
controllerA background loop that reconciles actual state toward desired state.
Module 02 · Getting Started

Architecture: Control Plane & Nodes

Every Kubernetes cluster splits into two planes: the control plane, which makes global decisions, and worker nodes, which run your workloads. Understanding these components makes every later concept click into place.

A. Control plane components

ComponentRole
kube-apiserverThe only entry point into the cluster. Validates and processes REST requests (from kubectl, controllers, kubelets), then reads/writes state to etcd. Stateless — can be horizontally scaled.
etcdA distributed, consistent key-value store. It is the single source of truth for the entire cluster's state. If etcd is lost without backup, the cluster's state is lost.
kube-schedulerWatches for newly created Pods with no assigned node, and picks the best node based on resource requests, constraints, affinity rules, and taints.
kube-controller-managerRuns many controller loops in one process: Node controller, ReplicaSet controller, Endpoints controller, Job controller, and more — each reconciling one resource type.
cloud-controller-managerBridges cluster and cloud-provider APIs (creating load balancers, attaching volumes, labeling nodes with cloud metadata). Absent on bare-metal / local clusters.

B. Worker node components

ComponentRole
kubeletThe agent on every node. Registers the node with the API server, receives Pod specs, and instructs the container runtime to start/stop containers. Continuously reports node & Pod status back.
kube-proxyMaintains network rules on each node (via iptables/IPVS) so traffic to a Service's virtual IP is load-balanced to the correct Pod.
container runtimeThe software that actually runs containers — containerd or CRI-O today (Docker Engine itself was deprecated as a direct runtime in v1.24 via the CRI — Container Runtime Interface).
Mental model. The control plane is the "brain" that only ever thinks in desired state. kubelets are the "hands" on each node that make it physically true. They never talk to each other directly — everything flows through the API server, which is why the API server being down doesn't crash running workloads, only the ability to change them.

C. High availability

In production, the control plane is normally replicated across 3 (or 5) machines: multiple kube-apiserver instances behind a load balancer, an odd-numbered etcd cluster (for quorum), and multiple scheduler/controller-manager instances using leader election — only one is active at a time, the rest are on standby.

D. Distributions & local setups

Managed cloud

EKS (AWS), GKE (Google), AKS (Azure) — control plane is fully managed for you.

Local dev

minikube, kind (Kubernetes-in-Docker), Docker Desktop's built-in cluster.

Self-managed

kubeadm, k3s (lightweight), Rancher, OpenShift.

Module 03 · Core Workloads

Pods — The Atomic Unit

A Pod is the smallest thing you can deploy in Kubernetes. Never a bare container — always a Pod.

A. What a Pod is

A Pod wraps one or more containers that are guaranteed to be scheduled together on the same node, and share:

  • A network namespace — one IP address per Pod; containers inside talk to each other via localhost.
  • Storage volumes — volumes defined on the Pod can be mounted into any of its containers.
  • A lifecycle — they're created and destroyed together.
Why not just run a container? Some apps need a tightly-coupled helper — a log shipper, a proxy, a file syncer — that must live and die with the main container and share its filesystem/network. That's a sidecar, and Pods are the mechanism that makes co-location an explicit, first-class concept instead of an ops hack.

B. Anatomy of a Pod manifest

Edit the YAML below and click Validate — the lab checks structure the way a lightweight linter would (required top-level keys, indentation, common mistakes).

pod-nginx.yaml

C. Multi-container Pods: patterns

Sidecar

Enhances the main container — e.g. a log-forwarding agent reading from a shared volume.

Ambassador

Proxies network connections out (e.g. a local proxy the main app calls, which handles retries/TLS).

Adapter

Normalizes the main container's output — e.g. reformatting logs/metrics into a standard shape.

D. Pod lifecycle phases

PhaseMeaning
PendingAccepted by the cluster, but one or more containers aren't running yet (image pulling, waiting to be scheduled).
RunningPod bound to a node, all containers created, at least one is running.
SucceededAll containers terminated successfully and won't restart (typical for Jobs).
FailedAll containers terminated, at least one in failure.
UnknownState couldn't be determined, usually a node communication problem.

Within Running, each container also has its own state: Waiting → Running → Terminated, visible via kubectl describe pod.

E. Init containers

Init containers run to completion, in order, before any app container starts — useful for waiting on a dependency or seeding a volume:

spec:
  initContainers:
    - name: wait-for-db
      image: busybox
      command: ['sh', '-c', 'until nslookup db-service; do sleep 2; done']
  containers:
    - name: app
      image: myapp:1.0

Module 04 · Core Workloads

ReplicaSets, Deployments & Rollouts

How Kubernetes keeps N copies of your app running, and how it ships new versions without downtime.

A. ReplicaSet

A ReplicaSet's only job: ensure a specified number of Pod replicas matching a label selector are running at all times. If you delete a Pod it manages, a new one appears within seconds.

apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: nginx-rs
spec:
  replicas: 3
  selector:
    matchLabels: { app: nginx }
  template:
    metadata:
      labels: { app: nginx }
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
You rarely write a ReplicaSet by hand. Deployments create and manage ReplicaSets for you, adding versioned rollout history on top — so in practice you always use a Deployment instead.

B. Deployment

A Deployment describes a desired application state; it creates a ReplicaSet, and when you change the Pod template (e.g. a new image tag), it creates a new ReplicaSet and orchestrates the transition between old and new.

deployment-web.yaml

C. Rollout strategies

RollingUpdate (default)

maxUnavailable caps how many old Pods can be down at once; maxSurge caps how many extra new Pods can exist above the desired count. Traffic shifts gradually — zero downtime if health checks are set correctly.

Recreate

Kill all old Pods, then create new ones. Simple but causes downtime — used when the app can't tolerate two versions running simultaneously (e.g. a schema-incompatible migration).

D. Rollout commands & rollback

kubectl apply -f deployment-web.yaml           # apply/update desired state
kubectl rollout status deployment/web-deployment
kubectl set image deployment/web-deployment web=myregistry/web:1.5.0
kubectl rollout history deployment/web-deployment
kubectl rollout undo deployment/web-deployment           # rollback to previous
kubectl rollout undo deployment/web-deployment --to-revision=2
Every revision is kept. Each rollout creates a new ReplicaSet, and old (scaled-to-zero) ReplicaSets stick around as rollout history, letting rollout undo instantly re-scale an old ReplicaSet back up instead of rebuilding Pods from scratch.

E. Scaling

kubectl scale deployment/web-deployment --replicas=10

This is imperative scaling for a one-off change; for ongoing automatic scaling see Module 13 — Autoscaling.

Module 05 · Core Workloads

Services & Service Discovery

Pods are ephemeral — they get new IPs every time they're recreated. A Service gives a stable identity in front of a changing set of Pods.

A. Why Services exist

A Deployment's Pods can be killed and rescheduled at any time, each time getting a new IP. A Service is a stable virtual IP + DNS name that load-balances across whichever Pods currently match its label selector — clients never need to know individual Pod IPs.

B. Service types

TypeBehaviorTypical use
ClusterIP (default)Internal virtual IP, reachable only inside the cluster.Backend-to-backend traffic.
NodePortOpens the same static port (30000–32767) on every node, forwarding to the Service.Simple external access / dev clusters.
LoadBalancerAsks the cloud provider to provision an external load balancer pointing at the Service.Production external access on a cloud.
ExternalNameMaps the Service name to an external DNS name via a CNAME — no proxying.Referencing an external database/API by an in-cluster name.
service-web.yaml

C. How Service routing actually works

The Endpoints (or EndpointSlice) controller watches Pods matching the Service's selector, and keeps a live list of their IP:port pairs. kube-proxy on every node programs iptables/IPVS rules so that traffic to the Service's ClusterIP is DNAT'd to one of those Pod IPs — chosen at random / round-robin.

D. DNS & service discovery

CoreDNS (the cluster's internal DNS server) auto-creates a record for every Service:

<service-name>.<namespace>.svc.cluster.local
# e.g. web-service.default.svc.cluster.local
# from the same namespace, just: web-service

E. Headless Services

Setting clusterIP: None gives you a "headless" Service — DNS resolves directly to the individual Pod IPs instead of a single virtual IP. Required for StatefulSets, where clients need to address specific replicas.

Module 06 · Core Workloads

Ingress

A single, smart entry point that routes HTTP(S) traffic to many Services based on hostname and path — instead of one LoadBalancer per Service.

A. Why Ingress

A LoadBalancer Service costs a real cloud load balancer per Service — expensive and wasteful for dozens of microservices. Ingress is a set of routing rules; an Ingress Controller (NGINX Ingress, Traefik, HAProxy, cloud-native ALB, etc.) reads those rules and does the actual proxying, usually behind just one LoadBalancer.

Ingress needs a controller. Creating an Ingress resource does nothing by itself — no controller is bundled with core Kubernetes. You must install one (e.g. ingress-nginx) for Ingress objects to take effect.
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-service
                port: { number: 80 }
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-service
                port: { number: 80 }
  tls:
    - hosts: ["shop.example.com"]
      secretName: shop-tls-cert

B. Path types

pathTypeMatches
ExactMatches the URL path exactly (case-sensitive).
PrefixMatches based on a URL path prefix split by /.
ImplementationSpecificInterpretation left to the Ingress controller.

C. TLS termination

The tls block references a Secret of type kubernetes.io/tls containing a certificate and private key; the controller terminates HTTPS there. In practice this Secret is usually auto-generated and renewed by cert-manager.

D. Ingress vs Gateway API

Looking forward. The newer Gateway API (a separate, more expressive CRD-based API — Gateway, HTTPRoute, etc.) is gradually superseding Ingress for advanced routing (traffic splitting, header-based rules, multi-namespace ownership) while Ingress remains the simple, ubiquitous option.
Module 07 · Configuration & Storage

ConfigMaps & Secrets

Externalize configuration and credentials from your container images, so the same image can run in dev, staging, and prod.

A. ConfigMap

Holds non-sensitive key-value configuration, consumable as environment variables, command-line args, or mounted files.

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: "info"
  MAX_CONNECTIONS: "100"
  app.properties: |
    retry.count=3
    timeout.ms=5000

As environment variables

envFrom:
  - configMapRef:
      name: app-config

As a mounted volume

volumes:
  - name: config-vol
    configMap:
      name: app-config
volumeMounts:
  - name: config-vol
    mountPath: /etc/config
Live updates. Mounted ConfigMap files update automatically (with a short propagation delay) when the ConfigMap changes — no Pod restart required, though your app must watch the file for changes. Env vars, by contrast, are only set at container start.

B. Secret

Same shape as a ConfigMap, but intended for sensitive data (passwords, tokens, keys) and stored base64-encoded (not encrypted by default — only obscured).

apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
data:
  username: YWRtaW4=        # base64 of "admin"
  password: c3VwZXJzZWNyZXQ=
Base64 is not encryption. Anyone with API read access to the Secret (or etcd access) can trivially decode it. Enable encryption at rest for etcd, restrict RBAC access to Secrets tightly, and consider an external secret manager (Vault, AWS Secrets Manager via External Secrets Operator) for anything highly sensitive.

C. Built-in Secret types

TypePurpose
OpaqueArbitrary user-defined key-value data (the default).
kubernetes.io/dockerconfigjsonCredentials for pulling images from a private registry.
kubernetes.io/tlsA TLS certificate + private key (used by Ingress).
kubernetes.io/service-account-tokenA token identifying a ServiceAccount.
secret-db.yaml
Module 08 · Configuration & Storage

Storage: Volumes, PV/PVC, StorageClasses

Containers are ephemeral by default — anything written to their filesystem disappears on restart. Kubernetes' storage system decouples "what storage does my Pod need" from "where does that storage physically live."

A. Volumes (Pod-scoped)

A basic volume lives and dies with its Pod, but survives individual container restarts within that Pod — useful for sharing data between sidecars, or scratch space.

TypeBehavior
emptyDirEmpty directory created when the Pod starts, deleted when the Pod is removed. Great for scratch space / cache / inter-container sharing.
hostPathMounts a path from the host node's filesystem. Powerful but risky — ties a Pod to node-local data.
configMap / secretProjects a ConfigMap/Secret's data as files.
persistentVolumeClaimMounts durable storage that outlives the Pod — see below.

B. The PV / PVC / StorageClass model

ObjectWho defines itRole
PersistentVolume (PV)Admin (or dynamically by a provisioner)A piece of real storage in the cluster — cloud disk, NFS share, etc.
PersistentVolumeClaim (PVC)App developerA request for storage ("10Gi, SSD, ReadWriteOnce") — abstracts away the physical volume.
StorageClassAdminA "template" for dynamically provisioning PVs on demand when a PVC is created, instead of pre-creating PVs by hand.
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-pvc
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: fast-ssd
  resources:
    requests:
      storage: 10Gi
---
# used inside a Pod/Deployment spec:
volumes:
  - name: data
    persistentVolumeClaim:
      claimName: data-pvc

C. Access modes

ModeMeaning
ReadWriteOnce (RWO)Mounted read-write by a single node at a time.
ReadOnlyMany (ROX)Mounted read-only by many nodes simultaneously.
ReadWriteMany (RWX)Mounted read-write by many nodes simultaneously (needs NFS-like backends).
ReadWriteOncePodMounted read-write by a single Pod only (stricter than RWO).

D. Reclaim policy

When a PVC is deleted, its bound PV's reclaimPolicy decides what happens to the underlying disk: Delete (destroy it — common for dynamic provisioning), or Retain (keep the disk and its data for manual recovery).

Module 09 · Configuration & Storage

Namespaces & Resource Quotas

Virtual clusters-within-a-cluster: how large teams share one Kubernetes cluster without stepping on each other.

A. What a Namespace is

A Namespace scopes names — two Deployments can both be called api as long as they're in different Namespaces. Most objects are namespaced (Pods, Deployments, Services, ConfigMaps); a few are cluster-wide (Nodes, PersistentVolumes, ClusterRoles, Namespaces themselves).

kubectl create namespace staging
kubectl get pods -n staging
kubectl get pods --all-namespaces

B. Default namespaces

NamespacePurpose
defaultWhere objects land if you don't specify one.
kube-systemCore Kubernetes components (CoreDNS, kube-proxy, etc.).
kube-publicReadable by all users, even unauthenticated ones — used for cluster-wide public info.
kube-node-leaseHolds Lease objects used for efficient node heartbeats.

C. ResourceQuota

Caps total resource consumption within a Namespace — total CPU, memory, and object counts — so one team can't starve another.

apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-quota
  namespace: staging
spec:
  hard:
    requests.cpu: "10"
    requests.memory: 20Gi
    limits.cpu: "20"
    limits.memory: 40Gi
    pods: "50"

D. LimitRange

Sets default and min/max resource requests/limits for individual Pods/containers within a Namespace, so developers who forget to set resources: still get sane defaults.

apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: staging
spec:
  limits:
    - default: { cpu: "500m", memory: "256Mi" }
      defaultRequest: { cpu: "100m", memory: "128Mi" }
      type: Container
Requests vs limits. requests is what the scheduler reserves for a container when placing it on a node (guaranteed minimum). limits is the hard ceiling — exceed the memory limit and the container is OOMKilled; exceed the CPU limit and it's throttled, not killed.
Module 10 · Advanced Workloads

StatefulSets, DaemonSets, Jobs & CronJobs

Deployments assume Pods are interchangeable. These four workload types cover the cases where they aren't.

A. StatefulSet — for stateful apps (databases, queues)

Unlike a Deployment's interchangeable Pods, a StatefulSet gives each replica a stable, unique identity that survives rescheduling:

  • Stable network identity: Pods are named predictably — web-0, web-1, web-2 — and each gets its own stable DNS name via a headless Service.
  • Stable storage: each replica gets its own PVC that follows it across rescheduling — web-0 always reattaches to the same disk.
  • Ordered deployment/scaling: Pods are created, updated, and deleted in strict order (0, 1, 2, ...), each waiting for the previous to be Running and Ready.
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres-headless
  replicas: 3
  selector:
    matchLabels: { app: postgres }
  template:
    metadata:
      labels: { app: postgres }
    spec:
      containers:
        - name: postgres
          image: postgres:16
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
    - metadata: { name: data }
      spec:
        accessModes: ["ReadWriteOnce"]
        resources: { requests: { storage: 20Gi } }
Reality check. Running a real, replicated database well (leader election, replication, failover) needs far more than a StatefulSet alone — most teams use a purpose-built Operator (e.g. Zalando's Postgres Operator, the Cloud Native PG operator) that builds on top of StatefulSets. More on Operators in Module 18.

B. DaemonSet — one Pod per node, automatically

Ensures a copy of a Pod runs on every node (or a matching subset), and automatically adds/removes it as nodes join/leave the cluster. Used for node-level agents:

  • Log collectors (Fluentd, Filebeat)
  • Monitoring agents (node-exporter)
  • Networking/CNI plugins (Calico, Cilium)
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter
spec:
  selector:
    matchLabels: { app: node-exporter }
  template:
    metadata:
      labels: { app: node-exporter }
    spec:
      containers:
        - name: node-exporter
          image: prom/node-exporter

C. Job — run to completion

A Job creates Pods and waits for them to successfully terminate, retrying on failure up to a limit — for batch work, migrations, one-off scripts.

apiVersion: batch/v1
kind: Job
metadata:
  name: db-migration
spec:
  backoffLimit: 3
  completions: 1
  parallelism: 1
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: myapp/migrate:1.0
          command: ["./migrate.sh"]

For parallel batch processing across many Pods, raise completions and parallelism — e.g. completions: 20, parallelism: 5 processes 20 units of work, 5 at a time.

D. CronJob — Jobs on a schedule

apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
spec:
  schedule: "0 2 * * *"     # standard cron syntax, UTC
  concurrencyPolicy: Forbid  # Allow | Forbid | Replace
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: myapp/backup:1.0

E. Quick comparison

WorkloadIdentity of PodsWhen it stopsUse case
DeploymentInterchangeableNever (keeps N running)Stateless web apps, APIs
StatefulSetStable, orderedNever (keeps N running)Databases, queues, clustered apps
DaemonSetOne per nodeNever (tracks nodes)Agents, log shippers, CNI
JobRuns to completionAfter successMigrations, batch jobs
CronJobJob on a timerAfter each scheduled runBackups, scheduled reports
Module 11 · Advanced Workloads

Scheduling: Affinity, Taints & Tolerations

How the scheduler decides which node runs which Pod, and how you influence — or constrain — that decision.

A. The default scheduling process

  1. Filtering — remove nodes that can't run the Pod (insufficient CPU/memory, port conflicts, unmatched node selectors, taints without matching tolerations).
  2. Scoring — rank remaining nodes (e.g. spreading Pods evenly, bin-packing, respecting affinity preferences).
  3. Binding — assign the Pod to the highest-scoring node.

B. nodeSelector — the simple version

spec:
  nodeSelector:
    disktype: ssd

C. Node affinity — the flexible version

spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: disktype
                operator: In
                values: ["ssd"]
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 80
          preference:
            matchExpressions:
              - key: zone
                operator: In
                values: ["us-east-1a"]
Rule typeMeaning
required...Hard constraint — the Pod won't schedule if unmet.
preferred...Soft constraint — the scheduler tries, but will still place the Pod elsewhere if needed. Uses a weighted score.

D. Pod affinity & anti-affinity

Place Pods relative to other Pods, not just node labels — e.g. spread replicas across failure domains, or co-locate a cache next to the service that uses it.

affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels: { app: web }
        topologyKey: "kubernetes.io/hostname"   # never 2 replicas on the same node

E. Taints & tolerations — the inverse mechanism

Affinity is a Pod saying "I prefer this node." A taint is a node saying "don't schedule here unless you explicitly tolerate me" — used to reserve nodes (GPU pools, dedicated hardware) or to mark unhealthy nodes.

# taint the node
kubectl taint nodes gpu-node-1 hardware=gpu:NoSchedule

# only Pods with a matching toleration can land there
spec:
  tolerations:
    - key: "hardware"
      operator: "Equal"
      value: "gpu"
      effect: "NoSchedule"
EffectMeaning
NoScheduleNew Pods without a matching toleration won't be scheduled here.
PreferNoScheduleScheduler tries to avoid it, but it's not a hard rule.
NoExecuteExisting Pods without the toleration are evicted too, not just blocked from new scheduling.
Working together. Node affinity attracts Pods to nodes; taints/tolerations repel Pods away from nodes unless explicitly allowed. Combining both is the standard way to build dedicated node pools (e.g. taint GPU nodes AND require GPU affinity, so GPU workloads land there and nothing else does).

F. Topology spread constraints

topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels: { app: web }

Evenly spreads Pods across zones/nodes/racks, capping the imbalance (maxSkew) — more precise than anti-affinity for even distribution.

Module 12 · Advanced Workloads

Health: Probes & Self-Healing

Kubernetes can't know your app is healthy unless you tell it how to check.

A. The three probe types

ProbeQuestion it answersOn failure
livenessProbeIs the container alive/unstuck?kubelet restarts the container.
readinessProbeIs the container ready to serve traffic right now?Pod is removed from Service endpoints (no restart) until it passes again.
startupProbeHas the app finished its (possibly slow) startup?Blocks liveness/readiness checks until it passes, then hands off — prevents slow-starting apps from being killed prematurely.
containers:
  - name: web
    image: myapp:1.0
    startupProbe:
      httpGet: { path: /healthz, port: 8080 }
      failureThreshold: 30
      periodSeconds: 2
    livenessProbe:
      httpGet: { path: /healthz, port: 8080 }
      initialDelaySeconds: 0
      periodSeconds: 10
      failureThreshold: 3
    readinessProbe:
      httpGet: { path: /ready, port: 8080 }
      periodSeconds: 5
      failureThreshold: 2

B. Probe mechanisms

MechanismHow it checks
httpGetHTTP GET; 200–399 = success.
tcpSocketAttempts a TCP connection; success = port accepts connections.
execRuns a command inside the container; exit code 0 = success.
grpcCalls the standard gRPC health-checking protocol.
A common outage cause. Liveness probes that check downstream dependencies (e.g. "can I reach the database?") cause cascading restarts — if the DB blips, kubelet restarts every app Pod simultaneously. Liveness should only check "is this process stuck," not "are my dependencies healthy" — that's what readiness is for.

C. restartPolicy

ValueBehavior
Always (default)Always restart on exit — used by Deployments/StatefulSets.
OnFailureRestart only on non-zero exit — typical for Jobs.
NeverNever restart — Job runs once per Pod, retries create new Pods instead.

D. Graceful shutdown

On termination, Kubernetes sends SIGTERM, then waits terminationGracePeriodSeconds (default 30s) before sending SIGKILL. Handle SIGTERM in your app to finish in-flight requests and close connections cleanly.

spec:
  terminationGracePeriodSeconds: 45
  containers:
    - name: web
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "sleep 5"]   # let load balancer deregister first
Module 13 · Advanced Workloads

Autoscaling: HPA, VPA, Cluster Autoscaler

Three independent, composable layers of autoscaling — how many Pod replicas, how big each Pod is, and how many nodes exist.

A. Horizontal Pod Autoscaler (HPA)

Adjusts the replica count of a Deployment/StatefulSet based on observed metrics.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-deployment
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80

Requires the metrics-server add-on for CPU/memory metrics, or a custom/external metrics adapter (e.g. Prometheus Adapter) for app-level metrics like requests-per-second or queue depth.

hpa-simulator — drag CPU load, watch it scale
min: 3
max: 20
current replicas: 3

B. Vertical Pod Autoscaler (VPA)

Instead of adding replicas, VPA adjusts a container's CPU/memory requests and limits based on historical usage — useful for workloads that can't scale horizontally (some databases) or to right-size requests automatically.

apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: web-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-deployment
  updatePolicy:
    updateMode: "Auto"   # Off (recommend only) | Initial | Auto
HPA + VPA conflict. Don't run HPA on CPU/memory and VPA on the same workload simultaneously — they can fight each other (VPA resizing while HPA is also reacting to the resulting utilization change). Use VPA in "Off" recommendation mode alongside HPA, or split metrics between them.

C. Cluster Autoscaler

Operates one level up: watches for Pods that are Pending because no node has room, and adds nodes to the cluster (via the cloud provider's API); removes underutilized nodes when their Pods could be rescheduled elsewhere. This is what actually lets HPA scale past your current node capacity.

LayerScalesReacts to
HPAPod replica countCPU/memory/custom metrics
VPAPer-Pod CPU/memory requestsHistorical usage
Cluster AutoscalerNumber of nodesUnschedulable (Pending) Pods / idle nodes

D. Newer alternative: Karpenter

An increasingly popular alternative to Cluster Autoscaler (originally AWS, now broader) that provisions right-sized nodes directly and faster, without pre-defined node groups.

Module 14 · Networking & Security

Networking: CNI, kube-proxy & DNS

Kubernetes networking rests on a small set of rules that every plugin must satisfy — the details of how are pluggable.

A. The fundamental networking model

  • Every Pod gets its own unique IP — no NAT between Pods.
  • Pods on any node can communicate with Pods on any other node without NAT.
  • A Pod sees its own IP the same way others see it (no translation from its own perspective).
  • Nodes can communicate with all Pods (and vice versa) without NAT.

This "flat network" model is what makes Services, DNS, and Ingress all work simply — nothing needs special-case NAT traversal logic.

B. CNI — Container Network Interface

Kubernetes itself doesn't implement Pod networking — it delegates to a CNI plugin, installed as a DaemonSet, that actually wires up each Pod's virtual network interface, IP allocation, and routing. Popular choices:

PluginKnown for
CalicoRich NetworkPolicy support, BGP routing, widely used in production.
CiliumeBPF-based — high performance, deep L3-L7 visibility, replaces kube-proxy entirely in some setups.
FlannelSimple overlay network, easy to run, fewer advanced features.
AWS/Azure/GCP CNICloud-native — Pods get real VPC IPs, integrating with existing cloud networking/security groups.

C. NetworkPolicy — firewalling Pod traffic

By default, all Pods can reach all other Pods. A NetworkPolicy restricts this — but only takes effect if the CNI plugin supports it (not all do; e.g. plain Flannel does not).

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-allow-from-web
  namespace: prod
spec:
  podSelector:
    matchLabels: { app: api }
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: web }
      ports:
        - protocol: TCP
          port: 8080
Default-deny pattern. A common baseline: apply an empty-selector policy denying all ingress/egress in a namespace, then add specific allow rules per app — "deny by default, allow explicitly," the same model as a real firewall.

D. CoreDNS

Runs as a Deployment in kube-system, watches Services/Endpoints via the API server, and serves DNS for the cluster — every Pod's /etc/resolv.conf points at it by default (via the ClusterFirst DNS policy).

E. kube-proxy modes

ModeMechanism
iptables (default, widely used)Programs iptables rules for Service routing; simple, proven, scales less gracefully with huge Service counts.
IPVSUses the kernel's IP Virtual Server — better performance and more load-balancing algorithms at large scale.
eBPF (e.g. via Cilium)Bypasses kube-proxy/iptables entirely for lower latency and richer policy.
Module 15 · Networking & Security

RBAC & Security

Who can do what, to which objects, in which namespaces — and how to run workloads with the least privilege they need.

A. Authentication vs authorization

Every API request goes through: Authentication (who are you? — client certs, tokens, OIDC, ServiceAccount tokens) → Authorization (are you allowed? — almost always RBAC today) → Admission Control (mutate/validate the request, e.g. injecting defaults or blocking policy violations).

B. RBAC building blocks

ObjectScopeDefines
RoleNamespacedA set of permitted verbs on resources, within one namespace.
ClusterRoleCluster-wideSame as Role, but can also cover cluster-scoped resources (Nodes, PVs) or be reused across namespaces.
RoleBindingNamespacedGrants a Role (or ClusterRole) to a user/group/ServiceAccount, within one namespace.
ClusterRoleBindingCluster-wideGrants a ClusterRole across the entire cluster.
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: staging
  name: pod-reader
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-binding
  namespace: staging
subjects:
  - kind: ServiceAccount
    name: ci-bot
    namespace: staging
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

C. ServiceAccounts

An identity for Pods (not humans) to authenticate to the API server — e.g. a Pod that needs to list other Pods, or call the API to create Jobs. Every namespace has a default ServiceAccount, but production practice is to create dedicated, minimally-privileged ones per workload.

spec:
  serviceAccountName: ci-bot
  automountServiceAccountToken: false   # disable if the Pod never calls the API

D. Pod security — restricting what containers can do

spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    fsGroup: 2000
    seccompProfile: { type: RuntimeDefault }
  containers:
    - name: web
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]

Pod Security Admission (built into the API server, replacing the deprecated PodSecurityPolicy) enforces cluster-wide baselines by labeling namespaces:

kubectl label namespace prod \
  pod-security.kubernetes.io/enforce=restricted
LevelMeaning
privilegedUnrestricted — full node access allowed.
baselineBlocks known privilege escalations, otherwise permissive.
restrictedHeavily locked down — enforces non-root, drops capabilities, blocks hostPath, etc. (production default recommendation).

E. Image & supply-chain security

  • Pin image tags/digests, never rely on floating :latest.
  • Scan images for CVEs in CI (Trivy, Grype) before they reach the cluster.
  • Use imagePullSecrets and private registries; restrict which registries are allowed via admission policy.
  • Sign images (cosign/Sigstore) and verify signatures at admission time.

Module 16 · Ecosystem

Helm — Package Manager

"apt/npm for Kubernetes" — templated, versioned, reusable bundles of manifests.

A. Why Helm

A real app is rarely one YAML file — it's a Deployment, a Service, a ConfigMap, an Ingress, an HPA, RBAC objects... and you need different values per environment. Helm solves this with:

  • Charts — a packaged, templated bundle of Kubernetes manifests.
  • Values — a YAML file of parameters injected into chart templates.
  • Releases — a named, versioned instance of a chart installed into a cluster, with upgrade/rollback history.

B. Chart structure

mychart/
├── Chart.yaml          # name, version, description
├── values.yaml         # default configuration values
├── templates/
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── ingress.yaml
│   └── _helpers.tpl    # reusable template snippets
└── charts/              # bundled sub-charts (dependencies)

C. Templating example

# templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-web
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: web
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          resources:
            {{- toYaml .Values.resources | nindent 12 }}
# values.yaml
replicaCount: 3
image:
  repository: myregistry/web
  tag: "1.4.0"
resources:
  requests: { cpu: 100m, memory: 128Mi }

D. Core commands

helm repo add bitnami https://charts.bitnami.com/bitnami
helm search repo nginx
helm install my-release bitnami/nginx --values values.yaml
helm upgrade my-release bitnami/nginx --set replicaCount=5
helm rollback my-release 1
helm uninstall my-release
helm list
helm template mychart/                    # render locally without installing
helm lint mychart/                        # validate a chart
GitOps pairing. In production, Helm charts are usually not run manually — a GitOps controller (ArgoCD, Flux) watches a Git repo of chart+values and continuously reconciles the cluster to match, giving you a full audit trail and automatic drift correction.
Module 17 · Ecosystem

Observability: Logs, Metrics & Events

Kubernetes gives you the raw signals; the ecosystem turns them into dashboards and alerts.

A. Logs

kubectl logs my-pod
kubectl logs my-pod -c sidecar-container     # multi-container pod
kubectl logs my-pod --previous               # logs from before the last restart
kubectl logs -f my-pod                       # follow / stream
kubectl logs -l app=web --all-containers      # by label, across pods

Kubernetes itself only keeps a rotating buffer of stdout/stderr per node — nothing is retained after a Pod (and node) is gone. Production clusters ship logs off-node via a DaemonSet (Fluentd/Fluent Bit/Vector) to a central store (Elasticsearch/Loki/Datadog).

B. Metrics

ToolRole
metrics-serverLightweight, in-memory CPU/memory metrics — powers kubectl top and HPA. No history.
PrometheusPulls (scrapes) time-series metrics from apps/exporters, stores history, powers alerting via Alertmanager.
GrafanaDashboards on top of Prometheus (or other data sources).
kubectl top nodes
kubectl top pods -n prod
kubectl top pods --containers

C. Events

Kubernetes emits Event objects for things happening to resources — scheduling decisions, image pull failures, probe failures — usually the fastest first place to look when debugging:

kubectl get events --sort-by=.lastTimestamp
kubectl describe pod my-pod   # includes recent Events at the bottom

D. Distributed tracing

For understanding a request's path across microservices, tools like Jaeger/Tempo (often paired with OpenTelemetry instrumentation) trace a single request end-to-end — logs and metrics alone can't show causality across services.

E. The three pillars, applied to K8s debugging

Metrics

"Something is wrong" — CPU spike, error rate up, latency up.

Logs

"What exactly happened" — stack traces, request details.

Traces

"Where in the call chain" — which service/hop introduced the latency or error.

Module 18 · Ecosystem

Custom Resources & Operators

How Kubernetes itself becomes extensible — teaching the API server about entirely new kinds of objects.

A. CustomResourceDefinition (CRD)

A CRD registers a brand-new resource type with the API server — after installing one, kubectl get, apply, RBAC, and the whole toolchain works on it exactly like a built-in object such as a Pod.

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: databases.example.com
spec:
  group: example.com
  names:
    kind: Database
    plural: databases
  scope: Namespaced
  versions:
    - name: v1
      served: true
      storage: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                engine: { type: string }
                size: { type: string }

Once installed, anyone can write:

apiVersion: example.com/v1
kind: Database
metadata:
  name: orders-db
spec:
  engine: postgres
  size: 20Gi

B. The Operator pattern

A CRD alone is just data — nothing happens when you create a Database object above unless something is watching it. An Operator is a custom controller (running as a Pod, written with a framework like Operator SDK or Kubebuilder) that runs the exact same reconciliation loop philosophy as built-in controllers, but encodes deep, human operational knowledge about a specific piece of software.

Famous examples: the Prometheus Operator (creates & manages Prometheus/Alertmanager from a ServiceMonitor CR), cert-manager (issues/renews TLS certs from a Certificate CR), database operators that handle failover and backups automatically.

C. Admission webhooks

The other major extension point — intercept requests to the API server before they're persisted:

TypeCan do
MutatingAdmissionWebhookModify the object (e.g. auto-inject a sidecar container, add default labels).
ValidatingAdmissionWebhookAccept/reject the object based on policy (e.g. block images without a digest, enforce label conventions).

Policy engines like OPA Gatekeeper and Kyverno are themselves built as validating/mutating webhooks, letting you write policy as data instead of Go code.

A-to-Z terms in one place, then a 10-question self-check.

A. Glossary

Admission Controller — code that intercepts API requests to mutate or validate them before persistence.
Affinity — rules that attract Pod scheduling toward certain nodes or other Pods.
CNI — Container Network Interface; the plugin standard for Pod networking.
ConfigMap — non-sensitive key-value configuration data injected into Pods.
Container Runtime — the software that runs containers on a node (containerd, CRI-O).
Control Plane — the components that make global cluster decisions (API server, etcd, scheduler, controller-manager).
CRD — CustomResourceDefinition; registers a new object type with the API server.
CronJob — runs Jobs on a cron schedule.
DaemonSet — ensures one Pod copy runs on every (matching) node.
Deployment — manages ReplicaSets to run and roll out stateless Pods.
etcd — the distributed key-value store holding all cluster state.
HPA — Horizontal Pod Autoscaler; scales replica count based on metrics.
Ingress — HTTP(S) routing rules to Services, handled by an Ingress Controller.
Job — runs Pods to completion for batch/one-off work.
kubectl — the CLI for talking to the Kubernetes API server.
kubelet — the node agent that runs Pods per the API server's instructions.
kube-proxy — programs per-node network rules for Service routing.
Label / Selector — key-value tags on objects, and queries that match them.
Namespace — a virtual partition scoping names and access within a cluster.
NetworkPolicy — firewall rules for Pod-to-Pod traffic.
Node — a single machine (VM or bare metal) in the cluster.
Operator — a custom controller encoding operational knowledge for a CRD-defined app.
Pod — the smallest deployable unit; one or more co-located containers.
Probe — a health check (liveness/readiness/startup) for a container.
PV / PVC — PersistentVolume (real storage) / PersistentVolumeClaim (a request for it).
RBAC — Role-Based Access Control; who can do what to which resources.
ReplicaSet — keeps a fixed number of identical Pods running.
Secret — like a ConfigMap, but for sensitive data (base64-encoded, not encrypted by default).
Service — a stable virtual IP/DNS name load-balancing across matching Pods.
ServiceAccount — an identity Pods use to authenticate to the API server.
StatefulSet — manages Pods with stable identity, storage, and ordering.
StorageClass — a template for dynamically provisioning PersistentVolumes.
Taint / Toleration — repels Pods from a node unless they explicitly tolerate it.
VPA — Vertical Pod Autoscaler; adjusts a container's CPU/memory requests over time.
