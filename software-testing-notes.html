01 · Fundamentals 4 topics
TC-01

What is Software Testing?

PASS

Software testing is the process of evaluating a system or its components to find whether it satisfies the specified requirements. In simple terms, it is the activity of executing a program with the intent of finding defects before the end user does.

  • Goal: verify the software works as expected and validate that it meets the user's real need.
  • Testing is not just "finding bugs" — it also builds confidence in quality, reduces risk, and checks performance, security and usability.
  • Software Engineering is the broader discipline: applying engineering principles (planning, design, construction, testing, maintenance) to build reliable software systems. Testing is one phase inside this larger engineering process.
Key ideaTesting can show the presence of defects, but it can never prove their absence — this is why testing is about risk reduction, not 100% guarantee.
TC-02

SDLC — Software Development Life Cycle

PASS

SDLC is the structured sequence of phases a software product passes through, from the idea stage to retirement. It gives engineering teams a predictable, repeatable process for building software.

diagram — sdlc-cycle.svg
01 Requirement
Gather & document what the business/user needs (BRS, SRS documents).
02 Design
Turn requirements into architecture — HLD (High Level Design) and LLD (Low Level Design).
03 Implementation
Developers write the actual code based on the design.
04 Testing
QA verifies the build against requirements and logs defects.
05 Deployment
The verified build is released to production / end users.
06 Maintenance
Bug fixes, patches, and enhancements after release feed back into new requirements.

Common SDLC models include Waterfall, V-Model, Iterative, Spiral and Agile — covered in Category 02.

TC-03

STLC — Software Testing Life Cycle

PASS

STLC is the sub-cycle inside SDLC that defines the specific, sequential phases carried out purely to test the software. Unlike SDLC, STLC begins as soon as requirements are available — testing does not wait for code to be complete.

diagram — stlc-phases.svg
  • Requirement Analysis: QA studies requirements to identify what's testable and raises queries.
  • Test Planning: Test lead defines scope, approach, resources, schedule — output is the Test Plan.
  • Test Case Development: Testers write test cases, test scripts, and prepare test data.
  • Environment Setup: The test lab / server / device configuration is prepared and smoke-checked.
  • Test Execution: Test cases are run, actual vs expected results compared, defects logged.
  • Test Closure: Team evaluates exit criteria, prepares the test summary report and captures lessons learned.
TC-04

Verification vs Validation

PASS

Verification asks "Are we building the product right?" Validation asks "Are we building the right product?" Both are needed for quality software.

AspectVerificationValidation
FocusProcess — checking documents, design, codeProduct — checking the actual working software
MethodReviews, walkthroughs, inspections (static)Executing the software (dynamic)
QuestionIs it built correctly per spec?Does it meet the user's actual need?
Performed byQA team, peer reviewersTesters, end users (UAT)
ExampleReviewing an SRS documentRunning the login module and checking it works
02 · Development Models 5 topics
TC-05

Waterfall Model

PASS

The oldest SDLC model — each phase must fully complete before the next one starts, flowing downward like a waterfall. Testing happens only after coding is fully done.

diagram — waterfall.svg
  • Best for: small projects with fixed, well-understood requirements.
  • Weakness: defects found late are expensive to fix; no going back once a phase closes.
TC-06

V-Model (Verification & Validation Model)

PASS

An extension of Waterfall where every development phase on the left has a matching testing phase on the right, forming a "V". Test planning starts in parallel with development, not after.

diagram — v-model.svg
  • Each dev phase maps 1:1 to a test level: Requirements ↔ Acceptance Testing, System Design ↔ System Testing, Architecture ↔ Integration Testing, Module Design ↔ Unit Testing.
  • Advantage: defects are caught earlier since test design starts alongside development. Disadvantage: still rigid — hard to accommodate late requirement changes.
TC-07

Agile Model

PASS

Software is built incrementally in short cycles called Sprints (usually 1–4 weeks). Each sprint delivers a working, tested slice of the product, and requirements can evolve based on feedback.

  • Core values: individuals & interactions, working software, customer collaboration, responding to change.
  • Testing is continuous and embedded in every sprint, not a separate late phase — this is called Agile Testing (see Category 11).
  • Common frameworks: Scrum (sprints, daily stand-up, sprint review/retro) and Kanban (continuous flow, WIP limits).
TC-08

Spiral Model

PASS

Combines iterative development with the risk-driven approach of Waterfall. Each "loop" of the spiral repeats four steps: Planning → Risk Analysis → Engineering → Evaluation, gradually growing the product.

  • Best for: large, complex, high-risk projects where requirements are unclear.
  • Heavy emphasis on risk analysis at every loop before committing more budget.
TC-09

Iterative Model

PASS

The system is built in repeated cycles (iterations), each producing a working version with more features than the last, rather than trying to fully define requirements up front.

  • Each iteration includes its own mini requirement → design → code → test loop.
  • Reduces risk versus Waterfall because problems surface early, in iteration 1 or 2, not at the very end.
03 · Levels of Testing 4 topics
TC-10

Unit Testing

PASS
diagram — testing-pyramid.svg

Unit testing verifies the smallest testable part of an application — usually a single function, method, or class — in isolation from the rest of the system. It is typically written and run by developers using frameworks like JUnit, NUnit, or PyTest.

  • Fast to run, cheap to maintain, and forms the base of the testing pyramid — the majority of automated tests should live here.
  • Dependencies are usually replaced with mocks/stubs so the unit is tested in true isolation.
TC-11

Integration Testing

PASS

Tests the interfaces and data flow between two or more integrated modules or services — e.g. does the "Order" module correctly call the "Payment" module?

  • Big Bang: integrate all modules at once and test together.
  • Top-Down: test from top-level modules downward, using stubs for lower modules not yet built.
  • Bottom-Up: test from lower-level modules upward, using drivers to simulate higher modules.
  • Sandwich/Hybrid: combination of Top-Down and Bottom-Up.
TC-12

System Testing

PASS

The complete, fully-integrated application is tested end-to-end against the full set of requirements, in an environment that mirrors production. It is a black box level test — performed by an independent QA team, not the developers.

  • Covers functional flows plus non-functional aspects: performance, security, usability, compatibility.
TC-13

Acceptance Testing (UAT)

PASS

The final level of testing, done to confirm the system is ready for delivery and meets business needs. User Acceptance Testing (UAT) is performed by actual end users or clients, not testers.

  • Alpha Testing: done in-house, by internal staff, before release to external users.
  • Beta Testing: done by real customers in their own environment, before the final public release.
04 · Testing Types 5 topics
TC-14

Functional Testing

PASS

Checks what the system does — verifying each function against the functional requirement specification, by feeding input and checking the output.

  • Sub-types: unit, integration, system, smoke, sanity, regression, and UAT — all check functional behaviour.
TC-15

Non-Functional Testing

PASS

Checks how well the system performs — not the business logic itself but its quality attributes.

  • Includes performance, load, stress, security, usability, compatibility, and reliability testing — detailed in Category 07.
TC-16

Regression Testing

PASS

Re-running existing test cases after a code change (bug fix, enhancement, or configuration change) to confirm that the change hasn't broken anything that used to work.

  • A prime candidate for automation, since the same suite is repeated over and over across builds.
TC-17

WhenImmediately after a new build is deployedAfter minor fixes / small changes, before deep regression

TC-18

Re-testing vs Regression Testing

PASS

05 · Testing Approaches 3 topics
TC-19

Black Box Testing

PASS
diagram — box-testing.svg

Testing based purely on inputs and outputs, without any knowledge of the internal code or logic. The tester treats the application as a "black box".

  • Used at the System and Acceptance testing levels; performed by independent QA testers.
  • Techniques used: equivalence partitioning, boundary value analysis, decision tables (see Category 06).
TC-20

White Box Testing

PASS

Testing with full visibility into the internal code, logic, and structure. Also called clear box, glass box or structural testing. Typically performed by developers.

  • Common techniques: statement coverage (every line executed), branch coverage (every if/else path taken), path coverage (every possible route through the code).
TC-21

Grey Box Testing

PASS

A hybrid: the tester has partial knowledge of the internals (e.g. database schema, API contracts) but tests mainly from the outside, like a user. Common in integration and security testing.

06 · Test Design Techniques 5 topics
TC-22

Equivalence Partitioning (EP)

PASS

Divides input data into groups ("partitions") that are expected to be treated the same way by the system. Instead of testing every possible value, you test one representative value per partition.

EXAMPLE — Age field accepts 18 to 60 Partitions: Invalid (< 18) · Valid (18–60) · Invalid (> 60)
Representative test values: 10 (invalid-low), 35 (valid), 75 (invalid-high)
TC-23

Boundary Value Analysis (BVA)

PASS

Defects cluster at the edges of input ranges, not the middle — so BVA tests values exactly on, just below, and just above each boundary.

diagram — bva-numberline.svg

For range 18–60, BVA test set: 17, 18, 19, 35, 59, 60, 61 — EP and BVA are almost always used together.

TC-24

Decision Table Testing

PASS

Used when the system's behaviour depends on a combination of conditions. Every combination of inputs (conditions) is mapped to its expected output (action) in a table.

EXAMPLE — Login: valid username AND valid password → grant access
RuleValid Username?Valid Password?Result
R1YYAccess granted
R2YNError: wrong password
R3NYError: wrong username
R4NNError: invalid credentials
TC-25

State Transition Testing

PASS

Used when a system behaves differently based on its current state and history — useful for workflows, login attempts, order status, etc.

diagram — atm-pin-states.svg

Test cases are derived from every valid and invalid state transition: Idle→PIN Entry, PIN Entry→Authorized, PIN Entry→Card Blocked (after 3 wrong attempts), etc.

TC-26

Use Case Testing

PASS

Test cases are derived from real-world use cases describing how an actor (user) interacts with the system to achieve a goal, including the main flow and alternate/exception flows.

  • Example use case: "Customer places an order" → main flow (browse → add to cart → checkout → pay), alternate flow (item out of stock), exception flow (payment fails).
07 · Non-Functional Deep Dive 5 topics
TC-27

Performance Testing

PASS

Evaluates speed, responsiveness, and stability of a system under a given workload — measuring metrics like response time, throughput, and resource usage (CPU/memory).

TC-28

Load, Stress & Volume Testing

PASS
TypeWhat it checks
Load TestingBehaviour under expected, normal-to-peak user load (e.g. 1,000 concurrent users)
Stress TestingBehaviour beyond normal capacity, to find the breaking point and how gracefully it fails
Volume TestingBehaviour when the database/system is flooded with a huge volume of data
Spike TestingBehaviour under a sudden, sharp increase/decrease in load

TC-29

Security Testing

PASS

Uncovers vulnerabilities that could lead to loss of data, revenue, or trust. Checks confidentiality, integrity, authentication, authorization, and non-repudiation.

  • Common checks: SQL injection, cross-site scripting (XSS), broken authentication, insecure data storage, penetration testing.
TC-30

Usability Testing

PASS

Checks how easy, intuitive, and user-friendly the application is — usually observed with real users completing real tasks, measuring learnability, efficiency, and error rate.

TC-31

Compatibility Testing

PASS

Confirms the software behaves consistently across different browsers, operating systems, devices, screen sizes, and network conditions.

08 · Test Management 4 topics
TC-32

Test Plan

PASS

A formal document describing the scope, approach, resources, and schedule of testing activities for a project. It is written once, at the start of a project or release.

  • Typical contents: objectives, scope (in/out), test approach, entry/exit criteria, resources, environment, risks, deliverables, schedule.
TC-33

Test Strategy

PASS

A high-level, organization-wide document describing the general testing approach — testing types to use, tools, standards. It's more stable and reusable than a Test Plan, which is project-specific.

TC-34

TC-35

Requirement Traceability Matrix (RTM)

PASS

A grid that maps each requirement to its corresponding test case(s), ensuring nothing is missed and every requirement has test coverage — critical for audits and impact analysis.

09 · Defect Management 2 topics
TC-36

Bug / Defect Life Cycle

FAIL → PASS

Every defect moves through a defined set of states from discovery to closure, so the whole team can track its status.

diagram — defect-lifecycle.svg
New
Defect logged for the first time by the tester.
Assigned
Test/dev lead assigns it to a developer.
Open
Developer starts analyzing/fixing the defect.
Fixed
Developer has applied a code fix.
Retest
Tester re-runs the originally failing test case.
Verified / Closed
Fix confirmed working — defect is closed.
Reopened
Fix didn't work — sent back to Assigned/Open.
Rejected
Reported behaviour is not actually a bug (as-designed / duplicate).

PASS

TC-39

Automation Frameworks

PASS
  • Linear/Record-Playback: simplest, records user actions directly — hard to maintain.
  • Modular: breaks the app into independent, reusable test modules/functions.
  • Data-Driven: test logic is separated from test data, which is fed from external files (CSV/Excel).
  • Keyword-Driven: actions are represented as keywords (e.g. "Click", "Type") readable by non-programmers.
  • Hybrid: combines data-driven and keyword-driven approaches.
  • BDD Framework: tests written in plain English (Given/When/Then) using tools like Cucumber.
TC-40

Selenium Basics

PASS

Selenium is the most widely used open-source framework for automating web browsers, supporting Java, Python, C#, and JavaScript.

  • WebDriver: core component that sends commands directly to the browser.
  • Locators: ID, Name, Class, XPath, CSS Selector — used to find page elements.
  • Selenium Grid: runs tests in parallel across multiple machines/browsers.
11 · Agile Testing 4 topics
TC-41

Agile Testing Quadrants

PASS

A model (Brian Marick) that maps testing activities across two axes: business-facing vs technology-facing, and supporting the team vs critiquing the product.

diagram — agile-quadrants.svg
TC-42

TDD — Test-Driven Development

PASS

Developers write an (initially failing) automated test before writing the actual code, then write just enough code to pass it.

Cycle: Red (write a failing test) → Green (write minimal code to pass) → Refactor (clean up code, keep tests green).

TC-43

BDD — Behaviour-Driven Development

PASS

Extends TDD by writing scenarios in plain, structured English so business, dev, and QA share one understanding, using the Given / When / Then format (Gherkin syntax, tool: Cucumber).

EXAMPLE — Gherkin scenario Given the user is on the login page
When they enter valid credentials and click Login
Then the dashboard page should be displayed
TC-44

Sprint Testing

PASS

Testing activity within a single Agile sprint: test cases are written and executed against each user story as soon as it's "dev complete," rather than waiting until the whole release is done.

  • A story is only marked "Done" once it meets the team's Definition of Done — which includes passing tests.
12 · Metrics & Tools 2 topics
TC-45

Test Metrics & KPIs

PASS
  • Test Case Execution %: (executed / total test cases) × 100
  • Defect Density: defects found ÷ size of module (e.g. per KLOC)
  • Defect Removal Efficiency (DRE): defects found before release ÷ total defects (before + after release)
  • Pass %: (passed test cases / executed test cases) × 100
  • Defect Leakage: defects missed by QA and found in production

13 · Practice Problems 6 worked problems
TC-47

Worked Problems

RUN ME
PROBLEM 1 — Equivalence Partitioning + BVA A text field accepts a password of length 8 to 12 characters. List the test cases using EP and BVA.
ANSWER EP: invalid-short (e.g. length 4), valid (e.g. length 10), invalid-long (e.g. length 16).
BVA: length 7 (invalid), 8 (min valid), 9 (valid), 11 (valid), 12 (max valid), 13 (invalid).
PROBLEM 2 — Severity & Priority The word "Sucess" is misspelled on a rarely-visited internal admin page. Assign severity and priority, with reasoning.
ANSWER Low severity (doesn't break functionality) and low priority (rarely seen, internal page) — safe to fix in a later release.
PROBLEM 3 — Test Case Writing Write one test case to verify a "Forgot Password" link.
ANSWER Steps: 1) Go to login page 2) Click "Forgot Password" 3) Enter a registered email 4) Click Submit.
Expected result: A password-reset email is sent and a confirmation message is shown on screen.
PROBLEM 4 — Bug Life Cycle A tester marks a defect "Fixed is not working" after retesting. What status should it move to next?
ANSWER Reopened — it goes back to the developer (Assigned/Open) instead of Verified/Closed.
PROBLEM 5 — Black Box vs White Box A tester checks branch coverage of an "if-else" block using the source code. Which testing approach is this?
ANSWER White Box Testing — it requires internal code knowledge and measures structural coverage.
PROBLEM 6 — SDLC vs STLC True or False: STLC can only begin after coding is 100% complete.
ANSWER False. STLC's Requirement Analysis and Test Planning phases start as soon as requirements are finalized — well before coding ends.
14 · Glossary A–Z
REF-01

Terms A to Z

PASS

AAcceptance Testing

Formal testing to confirm the system meets business/user needs, done before release.

BBlack Box Testing

Testing without knowledge of internal code, based only on inputs and outputs.

CCode Coverage

The percentage of source code executed by a test suite (statement, branch, path).

DDefect

A flaw in software that causes it to behave in an unintended way; also called a bug.

EEquivalence Partitioning

Dividing input data into groups expected to be handled the same way by the system.

FFunctional Testing

Testing that verifies each function of the software against its requirement.

GGrey Box Testing

Testing with partial knowledge of internal structure, combining black and white box.

HHotfix

An urgent, unplanned fix pushed directly to production to resolve a critical defect.

IIntegration Testing

Testing the interfaces and interaction between two or more integrated modules.

JJIRA

A widely used tool for tracking defects, user stories, and test management.

KKeyword-Driven Testing

An automation framework where test actions are represented as readable keywords.

LLoad Testing

Testing system behaviour under expected, real-world levels of concurrent usage.

MMock Object

A fake object that simulates the behaviour of a real dependency during unit testing.

NNegative Testing

Testing the system with invalid, unexpected, or malformed input to confirm graceful handling.

OOrthogonal Array Testing

A technique that tests all pairwise input combinations with a minimal number of test cases.

PPriority

How urgently a defect should be fixed, from a business standpoint.

QQuality Assurance (QA)

The process-focused discipline of preventing defects by improving how software is built.

RRegression Testing

Re-running existing tests to confirm a recent change hasn't broken existing functionality.

SSmoke Testing

A quick check that core functionality works before deeper testing begins.

TTest Case

A detailed set of steps, data, and expected results used to verify a specific behaviour.

UUnit Testing

Testing the smallest testable piece of code — a function, method, or class — in isolation.

VVerification

Confirming the product is being built correctly, according to specification.

WWhite Box Testing

Testing with full knowledge of the internal code, logic, and structure.

XXSS (Cross-Site Scripting)

A security vulnerability where malicious scripts are injected into trusted web pages.

YY2K Testing

Historic compliance testing to confirm systems correctly handled the year-2000 date rollover.

ZZero-Day Vulnerability

A previously unknown security flaw exploited before a fix is available.
