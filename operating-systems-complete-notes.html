Foundations · 01

What is an Operating System?

The operating system is the program that runs at all times on the computer — usually called the kernel — sitting between the physical hardware and every application you run. Everything else (a browser, a compiler, a game) is either a system program shipped with the OS or an application program.

Definition

An Operating System (OS) is system software that manages computer hardware and software resources, and provides common services for computer programs. It acts as an intermediary between the user/applications and the hardware.

1.1Two ways to think about an OS

VIEW A

Resource Manager

The OS allocates CPU time, memory, disk space, and I/O devices among competing processes — deciding who gets what, when, and for how long, to maximize utilization and fairness.

VIEW B

Extended / Virtual Machine

The OS hides messy hardware details (disk sectors, interrupt lines, register sets) and exposes clean abstractions instead — files instead of disk blocks, processes instead of raw CPU registers.

1.2The layers of a computer system

From the bottom up, a computer system is typically organized in layers, each hiding the complexity of the one below it:

LayerExamplesTalks to
HardwareCPU, memory, disks, NIC, GPUProvides raw computing resources
Operating SystemKernel, drivers, system daemonsControls & coordinates hardware for programs above
System & Application ProgramsCompilers, shells, browsers, gamesDefine how the system's resources are used to solve problems
UsersPeople, other machines, other programsIssue requests, consume output

1.3Why not run programs directly on hardware?

In principle you could — early computers did. But without an OS, every program would need to know how to talk to every disk controller, every printer, every network card, and would need to cooperate perfectly with every other program sharing the machine. The OS exists to remove that burden:

  • Abstraction — a program calls write(), not "move the disk head to cylinder 402."
  • Resource sharing — dozens of processes share one CPU and one RAM pool safely.
  • Protection & isolation — one crashing app should not corrupt another's memory.
  • Standard interface — the same open() call works whether the file lives on an SSD or a USB stick.
Mental model: think of the OS as an operating-room nurse: it doesn't do the surgery (your application logic), but it hands the surgeon (the CPU) exactly the right instrument at exactly the right time, keeps the room sterile (protection), and makes sure two surgeons never grab the same scalpel at once (synchronization).
Foundations · 02

Goals & Functions of an OS

Every OS, from a smartwatch's firmware to a datacenter hypervisor, is built around the same handful of core responsibilities.

01

Process Management

Create, schedule, suspend, resume, and terminate processes and threads; switch the CPU between them.

02

Memory Management

Allocate and reclaim RAM, translate virtual to physical addresses, and swap data to disk when RAM is scarce.

03

File & Storage Management

Organize persistent data into files and directories, and manage free/used space on disks.

04

Device / I/O Management

Talk to keyboards, disks, network cards, and GPUs through a uniform driver interface.

05

Protection & Security

Keep processes and users from interfering with — or spying on — each other, and authenticate who's allowed to do what.

06

User Interface

Expose a shell, GUI, or API so humans and programs can actually issue commands.

07

Networking

Implement protocol stacks (TCP/IP) so processes on different machines can communicate.

08

Error Detection

Detect hardware faults, memory errors, and software bugs, and respond without crashing the whole system.

2.1Convenience vs. Efficiency

OS design constantly balances two competing goals:

GoalWhat it optimizes forExample trade-off
ConvenienceMake the system easier and more pleasant to useA friendly GUI file manager costs CPU cycles a raw ls wouldn't.
EfficiencyMaximum use of hardware resources (throughput, low overhead)Servers strip GUIs entirely to save RAM and CPU for real workloads.
Foundations · 03

Types of Operating Systems

Operating systems evolved as hardware and usage patterns changed. Each "generation" below solved a specific bottleneck of the one before it.

Batch Operating Systems

Jobs (punch cards, later files) are collected into a batch and run one after another with no interaction. A human operator loads a "batch," the OS runs each job to completion, and output is collected later. No CPU idling between jobs, but zero interactivity and poor turnaround for any single job.

Multiprogrammed Operating Systems

Several jobs sit in memory at once. When the running job blocks on I/O, the CPU switches to another ready job instead of idling. This is the key idea that makes CPU utilization high — the OS must now choose which job runs next (CPU scheduling).

Time-Sharing (Multitasking) Operating Systems

Multiprogramming taken further: the CPU switches between jobs so fast (milliseconds) that each user feels they have the machine to themselves. This is the model behind modern desktops — you "feel" your browser, IDE, and music player all run "simultaneously."

Multiprocessor (Parallel / Tightly-Coupled) Systems

Two or more CPUs share memory and a single OS instance. Gives higher throughput, graceful degradation if one CPU fails, and true parallel execution — not just interleaving.

Distributed Operating Systems

Multiple independent computers, each with their own memory, connected by a network, presenting (to varying degrees) a single-system image. Enables resource sharing, load distribution across sites, and resilience — if one node dies, others carry on.

Network Operating Systems

A looser cousin of distributed OS: each machine keeps its own local OS and autonomy, but the OS provides awareness of, and login/file access to, other machines over a network (e.g. classic Windows Server / Novell NetWare style file & print sharing).

Real-Time Operating Systems (RTOS)

Correctness depends on when results appear, not just whether. Hard real-time systems (aircraft control, pacemakers) must never miss a deadline. Soft real-time systems (video streaming, gaming) tolerate occasional missed deadlines with degraded quality.

Mobile & Embedded Operating Systems

Purpose-built for constrained power, memory, and screen size — Android, iOS, embedded RTOS variants (FreeRTOS, Zephyr) inside routers, cars, and appliances.

Foundations · 04

Operating System Structures

"OS structure" describes how the kernel's internal code is organized — a design decision that trades off performance against safety, and simplicity against extensibility.

SIMPLE

Monolithic Structure

The entire OS — scheduler, file system, drivers, networking — runs as one large program in kernel mode. Fast (no cross-boundary calls) but a bug anywhere can crash the whole system. Linux and classic UNIX kernels are monolithic (with loadable modules).

CLASSIC

Layered Approach

The OS is divided into layers, each built only on the services of the layer below (Layer 0 = hardware, Layer N = user interface). Easy to debug and verify layer by layer, but rigid layering hurts performance and isn't always achievable in practice.

MINIMAL

Microkernel

Only the bare essentials — inter-process communication, basic scheduling, minimal memory management — run in kernel mode. File systems, drivers, and networking run as user-mode servers. More robust and secure (a crashed driver doesn't crash the kernel) but slower due to message-passing overhead. Example: Minix, QNX, seL4.

FLEXIBLE

Modules (Loadable Kernel Modules)

A monolithic-style core with dynamically loadable modules for drivers and file systems — the best of both worlds: near-monolithic speed with the flexibility to add/remove functionality at runtime without a reboot. Linux kernel modules (.ko) and Windows drivers work this way.

MIXED

Hybrid Kernel

Runs most services in kernel space for speed (like a monolith) but keeps a microkernel-style modular internal design for maintainability. Windows NT and macOS's XNU kernel are hybrid.

RESEARCH

Exokernel

Pushes abstraction almost entirely out of the kernel — the kernel just multiplexes raw hardware safely and lets each application (via library OSes) implement its own abstractions. Maximizes flexibility and performance for specialized workloads at the cost of huge application complexity.

4.1Kernel Mode vs. User Mode

Nearly all modern CPUs support at least two privilege levels, enforced in hardware via a mode bit:

User ModeKernel Mode
RunsApplications, most librariesOS core, drivers
Can execute privileged instructions?NoYes
Direct hardware access?No — must ask via system callYes
A crash here......kills one process...can panic the whole machine

A trap (software interrupt) is how user mode requests kernel mode's help — this is exactly the mechanism behind a system call.

Foundations · 05

System Calls & System Programs

A system call is the programming interface a process uses to request a service from the kernel — the only sanctioned doorway between user mode and kernel mode.

5.1How a system call actually works

Application calls a library function

e.g. your C program calls read(fd, buf, n) from the standard library — this is not the kernel yet, just a wrapper.

Wrapper loads a syscall number and traps

The syscall number and arguments are placed into registers, then a special trap instruction (e.g. syscall/int 0x80 on x86) is executed.

CPU switches to kernel mode

The trap raises the privilege level and jumps to a fixed kernel entry point — the process cannot jump anywhere else in the kernel.

Kernel dispatches via the syscall table

The kernel looks up the syscall number in a table of function pointers and executes the corresponding kernel routine, validating all arguments first.

Result returns to user mode

The CPU mode bit flips back, control returns to the instruction right after the trap, and the library wrapper hands the result back to your program.

5.2Categories of system calls

CategoryPurposeExamples (POSIX)
Process controlCreate/end processesfork(), exec(), exit(), wait()
File managementCreate/read/write filesopen(), read(), write(), close()
Device managementRequest/release devicesioctl(), read(), write()
Information maintenanceGet/set system datagetpid(), alarm(), sleep()
CommunicationInter-process data exchangepipe(), shmget(), mmap()
ProtectionControl resource accesschmod(), umask(), chown()

5.3System Programs

System programs (a.k.a. system utilities) ship with the OS but aren't part of the kernel — compilers, assemblers, text editors, file utilities (ls, cp), and the command interpreter (shell) itself. They give users a way to accomplish tasks without writing raw system-call code.

fork_exec_wait.c — the classic UNIX process-creation pattern
// Parent creates a child, child replaces itself with /bin/ls, parent waits
pid_t pid = fork();

if (pid == 0) {
    // --- child process ---
    execlp("/bin/ls", "ls", "-l", NULL);
    // execlp only returns if it failed
    perror("exec failed");
    exit(1);
} else if (pid > 0) {
    // --- parent process ---
    int status;
    wait(&status);       // block until child terminates
    printf("child finished\n");
} else {
    perror("fork failed");
}
Foundations · 06

The Boot Process

Booting is how a computer goes from "power off" to "kernel running and scheduling processes." It's a bootstrap problem — the CPU can't run the OS until something small loads it, but that loader itself has to come from somewhere.

Firmware initializes (BIOS / UEFI)

On power-on, the CPU starts executing firmware baked into a ROM chip on the motherboard. It runs a Power-On Self Test (POST), initializes basic hardware (RAM controller, chipset), and finds a boot device.

Firmware loads the bootloader

BIOS reads the Master Boot Record (first 512 bytes of the boot disk); UEFI reads an EFI System Partition. Either way, this loads a tiny bootloader (GRUB, Windows Boot Manager, U-Boot) into memory.

Bootloader loads the kernel

The bootloader locates the actual kernel image on disk, decompresses it into memory, sets up an initial minimal environment, and jumps to the kernel's entry point.

Kernel initializes itself

The kernel sets up memory management, interrupt handlers, schedules its first internal structures, detects and initializes hardware, and mounts a temporary/initial root filesystem.

Kernel starts the first user-space process

Linux starts PID 1 (systemd/init); this process then starts all other system services (networking, login, GUI) according to its configuration.

System reaches a login / ready state

Once essential services are up, the user sees a login prompt (text or graphical) — the machine is now in normal, time-sharing operation.

Firmware note: UEFI (the modern replacement for legacy BIOS) supports Secure Boot — cryptographically verifying each stage (firmware → bootloader → kernel) hasn't been tampered with, closing off a whole class of boot-time malware (bootkits).
Process Management · 07

Process Concept

A process is a program in execution — an active entity with a program counter, registers, and its own memory, as opposed to a program, which is just a passive file of instructions sitting on disk.

7.1Memory layout of a process

SegmentContentsGrows how?
TextCompiled program instructionsFixed, read-only
DataGlobal & static variablesFixed size, set at load time
HeapDynamically allocated memory (malloc/new)Grows upward at runtime
StackFunction call frames, local variables, return addressesGrows downward at runtime

7.2Process States

As a process executes, it moves between states. Every OS textbook uses roughly this five-state model:

NEW
→ admitted →
READY
→ dispatch →
RUNNING
→ exit →
TERMINATED
RUNNING
← I/O or event wait ←
WAITING
← I/O or event completion ←
READY
  • New — process is being created.
  • Ready — waiting to be assigned a CPU; sitting in the ready queue.
  • Running — instructions are actively being executed.
  • Waiting (Blocked) — waiting for some event (I/O completion, a signal).
  • Terminated — finished execution; waiting to be removed from the process table.

7.3The Process Control Block (PCB)

The kernel represents each process with a PCB — a data structure holding everything needed to stop the process and later resume it exactly where it left off.

Identification

Process ID (PID), parent PID, user ID.

CPU state

Program counter, general-purpose registers, condition codes, stack pointer.

Scheduling info

Process state, priority, scheduling queue pointers.

Memory info

Base/limit registers, page tables, segment tables.

Accounting

CPU time used, time limits, process start time.

I/O status

List of open files, allocated I/O devices.

7.4Context Switching

A context switch is the act of saving the state (registers, PC) of the currently running process into its PCB, and loading the saved state of the next process to run. It's pure overhead — no useful work happens during the switch itself — so OS designers work hard to make it fast (often using dedicated hardware support for register-set swaps).

Process vs. Program: notepad.exe on disk is a program — inert. Open two windows of it and you have two processes, each with its own PCB, memory space, and PID, even though they share the exact same code.
Process Management · 08

Process Scheduling Queues & Schedulers

As processes enter the system, the OS places them into different queues, and specialized schedulers decide when to move a process from one queue to another.

8.1Queues

QueueHolds processes that are…
Job queueAll processes in the system, including ones not yet in memory
Ready queueIn memory, waiting for a chance to run on the CPU
Device / wait queuesWaiting for a specific I/O device or event to complete

8.2The Three Schedulers

RUNS RARELY

Long-Term Scheduler (Job Scheduler)

Decides which jobs are admitted into memory to become "ready" processes at all. Controls the degree of multiprogramming. Mostly relevant to batch systems; time-sharing systems often skip it (every job is admitted immediately).

RUNS OFTEN

Short-Term Scheduler (CPU Scheduler)

Picks which ready process runs next on the CPU. Must be extremely fast — it may run every few milliseconds. This is the scheduler behind all the algorithms in the next section.

TIME-SHARING

Medium-Term Scheduler

Temporarily removes ("swaps out") processes from memory to reduce the degree of multiprogramming — e.g. under memory pressure — and later swaps them back in. Adds a swapping layer between "in memory, ready" and "on disk, suspended."

8.3CPU–I/O Burst Cycle

Process execution alternates between CPU bursts (computation) and I/O bursts (waiting on a device). Scheduling algorithms are designed around the statistical shape of these bursts — most processes have many short CPU bursts and a few long ones.

Process Management · 09

CPU Scheduling Algorithms

CPU scheduling picks which ready process gets the processor next. Algorithms are judged on CPU utilization, throughput, turnaround time, waiting time, and response time — and different algorithms optimize for different mixes of these.

9.1Key metrics

MetricFormula
Completion Time (CT)Time at which the process finishes execution
Turnaround Time (TAT)CT − Arrival Time
Waiting Time (WT)TAT − Burst Time
Response Time (RT)Time from arrival to first time getting the CPU

9.2The algorithms

FCFS — First Come, First Served

Non-preemptive; processes run strictly in arrival order, like a single checkout line. Simple, but a long job at the front causes the convoy effect — everyone behind it waits needlessly.

SJF — Shortest Job First

Non-preemptive; always run whichever ready process has the smallest total burst time. Provably minimizes average waiting time — but requires knowing burst times in advance (usually estimated) and can starve long jobs.

SRTF — Shortest Remaining Time First

The preemptive version of SJF: if a new process arrives with a shorter remaining burst than the currently running one, it preempts immediately. Optimal for average waiting time among preemptive schemes, at the cost of more context switches.

Priority Scheduling

Each process gets a priority number; the highest-priority ready process runs (can be preemptive or non-preemptive). Risk: low-priority processes may starve forever — solved with aging (gradually increasing the priority of processes that wait too long).

Round Robin (RR)

Each process gets a fixed time quantum; if it doesn't finish, it's preempted and sent to the back of the ready queue. Fair and responsive (great for time-sharing), but a too-small quantum wastes time on context switches, and a too-large quantum degenerates into FCFS.

Multilevel Queue Scheduling

The ready queue is split into separate queues by process category (e.g. "foreground/interactive" vs "background/batch"), each with its own algorithm, and a fixed or priority-based policy decides how CPU time is split between queues.

Multilevel Feedback Queue (MLFQ)

Like multilevel queue, but processes can move between queues based on behavior — a CPU-bound process that uses its whole quantum gets demoted to a lower-priority, longer-quantum queue; an I/O-bound process that yields early stays high-priority. Self-tuning and used in real kernels (Windows, older Solaris).

Process Management · 10

Threads & Multithreading

A thread is the basic unit of CPU utilization — a lightweight process. A traditional (single-threaded) process has one thread of control; a multithreaded process has several, each with its own program counter, register set, and stack, but sharing the same code, data, and open files.

10.1Why threads?

Responsiveness

A GUI stays interactive even while one thread does heavy work in the background.

Resource sharing

Threads in one process share memory naturally — no IPC needed for that data.

Economy

Creating/context-switching a thread is far cheaper than a whole process (no new address space).

Scalability

Threads can run in parallel across multiple CPU cores for real speedup.

10.2User Threads vs. Kernel Threads

User-Level ThreadsKernel-Level Threads
Managed byA user-space thread library, kernel unawareThe kernel directly
Switch costVery cheap (no kernel trap)More expensive (kernel involved)
Blocking syscallCan block the entire processOnly that thread blocks
True parallelismNot without kernel supportYes, across cores

10.3Multithreading Models

Many-to-One

Many user threads map to a single kernel thread. Fast to manage, but one blocking call stalls all threads and there's no parallelism.

One-to-One

Every user thread gets its own kernel thread. Enables true parallelism (used by Linux and Windows), at the cost of kernel-thread creation overhead — usually capped.

Many-to-Many

Multiplexes many user threads onto a smaller-or-equal number of kernel threads — the kernel can schedule several onto separate cores while the library manages the rest, balancing flexibility and performance.

pthreads.c — creating and joining threads (POSIX)
void* worker(void* arg) {
    printf("thread running, arg=%d\n", *(int*)arg);
    return NULL;
}

int main() {
    pthread_t t1, t2;
    int a = 1, b = 2;

    pthread_create(&t1, NULL, worker, &a);
    pthread_create(&t2, NULL, worker, &b);

    pthread_join(t1, NULL);   // wait for t1 to finish
    pthread_join(t2, NULL);   // wait for t2 to finish
    return 0;
}
Process Management · 11

Multiprocessor & Multicore Scheduling

Modern chips pack multiple cores (and multiple threads per core via SMT/hyper-threading), which turns scheduling into a placement problem, not just an ordering problem.

11.1Symmetric vs. Asymmetric Multiprocessing

Asymmetric Multiprocessing (AMP)

One "master" processor makes all scheduling and I/O decisions; others just execute user code. Simpler, less contention on shared data — but the master can become a bottleneck.

Symmetric Multiprocessing (SMP)

Every processor is self-scheduling and equally capable of running kernel or user code, typically sharing one ready queue (or per-core queues). What virtually all modern general-purpose OSes use.

11.2Key multicore scheduling concerns

  • Load balancing — keeping work evenly spread across cores (push migration vs pull migration).
  • Processor affinity — preferring to keep a process on the same core to reuse warm cache lines (soft affinity: preference; hard affinity: guarantee).
  • NUMA awareness — on Non-Uniform Memory Access systems, scheduling a process near the memory it uses avoids costly cross-node memory latency.
  • Gang scheduling — scheduling a set of related threads to run simultaneously across cores, useful for tightly-coupled parallel applications.
Amdahl's Law: speedup from parallelization is capped by a program's sequential portion: Speedup ≤ 1 / (S + (1−S)/N), where S is the serial fraction and N is the core count. Ten cores can't give a 10× speedup if 20% of the work is inherently sequential.
Synchronization & Deadlock · 12

The Critical Section Problem

When multiple processes or threads share data, uncoordinated access produces a race condition — the final result depends on the unpredictable timing of execution.

Critical Section

The segment of code where a process accesses shared resources (variables, files, data structures) that must not be concurrently accessed by more than one process.

12.1Three requirements for a correct solution

Mutual Exclusion

If one process is executing in its critical section, no other process may execute in its critical section at the same time.

Progress

If no process is in its critical section, and some processes want to enter, only those not in their remainder section may participate in deciding who enters next — and that decision can't be postponed indefinitely.

Bounded Waiting

There must be a limit on how many times other processes can enter their critical section after a process has requested entry and before that request is granted.

12.2Peterson's Solution

A classic software-only solution for two processes, using a turn variable and a flag[] array. Rarely used in real systems (modern CPUs reorder memory operations, breaking the assumptions it relies on) but foundational for understanding the problem.

petersons.c — two-process mutual exclusion
int turn;
bool flag[2];   // flag[i] = true means process i wants to enter

// Process i (the other is process j)
flag[i] = true;
turn = j;                       // politely let the other go first
while (flag[j] && turn == j) {
    // busy-wait — spin until it's our turn
}

/* ---- critical section ---- */

flag[i] = false;             // leave critical section

/* ---- remainder section ---- */

This satisfies all three properties: flag[] guarantees mutual exclusion, and turn breaks the tie for progress and bounded waiting.

12.3Hardware support

Real systems rely on atomic hardware instructions instead of pure software solutions:

InstructionWhat it does atomically
test_and_set()Reads a boolean, sets it to true, returns the old value — all as one indivisible step
compare_and_swap()Updates a value only if it still equals an expected old value
Synchronization & Deadlock · 13

Semaphores, Mutex Locks & Monitors

Real operating systems provide higher-level synchronization tools built on hardware atomics, so application programmers don't hand-roll Peterson-style spin loops.

13.1Mutex Lock

The simplest tool: a binary lock with two operations, acquire() and release(). Only one thread can hold it at a time; others calling acquire() block until it's released.

13.2Semaphores

An integer variable accessed only through two atomic operations, traditionally named wait() (P, from Dutch proberen) and signal() (V, verhogen):

semaphore.c — wait and signal
wait(semaphore *S) {
    while (S->value <= 0)
        ; // busy wait (or block, in real implementations)
    S->value--;
}

signal(semaphore *S) {
    S->value++;
}
TypeValue rangeUse
Binary semaphore0 or 1Behaves like a mutex lock
Counting semaphoreAny non-negative integerControls access to a resource with multiple instances (e.g. a pool of 5 printers)
Busy waiting vs. blocking: the pseudocode above spins in a loop wasting CPU cycles. Real implementations instead put the waiting process on a queue associated with the semaphore and put it in the waiting state — a context switch away — only waking it when signal() is called.

13.3Monitors

A higher-level abstraction: a language construct that bundles shared data with the procedures that operate on it, guaranteeing only one process can be "active" inside the monitor at once — the compiler enforces mutual exclusion, not the programmer. Monitors use condition variables (wait()/signal() on a condition, not a count) for waiting on specific circumstances inside the monitor.

Common bugs these tools must avoid: forgetting to release a lock, releasing a lock you don't hold, and nesting locks inconsistently across threads (a leading cause of deadlock — see section 15).
Synchronization & Deadlock · 14

Classical Synchronization Problems

These textbook problems are stress tests for synchronization tools — each models a real coordination pattern that shows up constantly in systems programming.

14.1Producer–Consumer (Bounded Buffer)

Producers add items to a fixed-size buffer; consumers remove them. Needs: producers block when the buffer is full, consumers block when it's empty, and no two threads touch the buffer index simultaneously.

producer_consumer.c — three semaphores
semaphore empty = N;   // counts free slots
semaphore full  = 0;   // counts filled slots
semaphore mutex = 1;   // protects the buffer itself

producer() {
    while (true) {
        item = produce_item();
        wait(empty);      // wait for a free slot
        wait(mutex);
        insert_item(item);
        signal(mutex);
        signal(full);     // announce a new filled slot
    }
}

consumer() {
    while (true) {
        wait(full);       // wait for a filled slot
        wait(mutex);
        item = remove_item();
        signal(mutex);
        signal(empty);    // announce a new free slot
        consume(item);
    }
}

14.2Readers–Writers

Multiple readers may read shared data concurrently, but a writer needs exclusive access. The classic "first" version favors readers (writers may starve); the "second" version favors writers (readers may starve) — real systems use a fair variant.

14.3Dining Philosophers

Five philosophers sit at a round table with one fork between each pair — a philosopher needs both forks to eat. Naively picking up "left fork, then right fork" can deadlock if everyone grabs their left fork simultaneously. Classic fixes: allow only 4 philosophers to sit at once, require picking up both forks atomically, or impose an asymmetric ordering (odd philosophers pick up left-then-right, even philosophers right-then-left).

Synchronization & Deadlock · 15

Deadlocks

A deadlock is a state where a set of processes are each waiting for a resource held by another process in the set — none can ever proceed.

15.1The Four Necessary Conditions (Coffman Conditions)

A deadlock can occur only if all four hold simultaneously:

1

Mutual Exclusion

At least one resource must be held in a non-shareable mode.

2

Hold and Wait

A process holding at least one resource is waiting to acquire additional resources held by others.

3

No Preemption

Resources cannot be forcibly taken away — only voluntarily released by the process holding them.

4

Circular Wait

A closed chain of processes exists, each waiting for a resource held by the next.

15.2Resource Allocation Graph

A directed graph with process nodes and resource nodes. A request edge (process → resource) means the process is waiting for it; an assignment edge (resource → process) means it's held. If the graph contains a cycle and each resource has only one instance, a deadlock exists. With multiple instances per resource, a cycle is necessary but not sufficient for deadlock.

Deadlock vs. Starvation: deadlock is a hard stop — the involved processes will never proceed without intervention. Starvation is a process waiting indefinitely while others keep proceeding — the system as a whole is still making progress, just not for that one process.
Synchronization & Deadlock · 16

Handling Deadlocks

There are four general strategies for dealing with deadlock, ordered roughly from most conservative to most permissive.

Prevention

Design the system so at least one of the four Coffman conditions can never hold — e.g. require processes to request all resources at once (breaks hold-and-wait), or impose a global resource-ordering rule (breaks circular wait). Safe but often kills concurrency/efficiency.

Avoidance

Allow the four conditions but grant resource requests dynamically only when doing so leaves the system in a safe state — a state from which there's a guaranteed order in which all processes can finish. The Banker's Algorithm (below) is the classic avoidance algorithm.

Detection & Recovery

Let deadlocks happen, periodically run a detection algorithm (essentially cycle-detection over an allocation graph), and recover by preempting resources or aborting one or more processes involved in the cycle.

Ostrich Algorithm

Ignore the problem entirely — assume deadlocks are rare enough that the cost of prevention/avoidance isn't worth it. This is what most general-purpose OSes (including Linux and Windows) actually do at the kernel level; deadlock handling is left to applications.

16.1Banker's Algorithm — Live Simulator

The Banker's Algorithm treats resource allocation like a cautious bank manager: never make a loan (grant a request) that could leave the bank unable to satisfy everyone eventually. It needs, per process: Max demand, current Allocation, and derives Need = Max − Allocation. A state is safe if there exists some order to finish all processes using the currently Available resources plus what's freed as each finishes.

Banker's Algorithm — Safety Check
ProcessAllocation (A B C)Max (A B C)Need (A B C)
safety_algorithm.pseudo
Work = Available
Finish[i] = false  for all i

repeat
    find i such that:
        Finish[i] == false  AND  Need[i] <= Work
    if found:
        Work += Allocation[i]
        Finish[i] = true
    else:
        break
until no such i found

if all Finish[i] == true:
    state is SAFE (the order processes finished in is a safe sequence)
else:
    state is UNSAFE (deadlock possible)

Address Binding & Contiguous Allocation

Before a program's instructions can run, its symbolic addresses (variable names, function labels) must be bound to actual memory addresses — at compile time, load time, or run time.

Binding TimeWhen addresses are fixedTrade-off
Compile timeAt compilation, if the load address is known in advanceFastest, but the process can never be relocated
Load timeWhen the program is loaded into memoryFlexible starting address, but still fixed once loaded
Execution timeDeferred until the instruction actually runs; needs hardware support (base/limit registers, MMU)Process can be moved (relocated) during execution — what virtually all modern systems use

17.1Logical vs. Physical Address Space

A logical (virtual) address is generated by the CPU; a physical address is what's actually loaded into the memory unit. The Memory Management Unit (MMU) is the hardware that translates logical to physical addresses at runtime — usually by adding a relocation register's value to every logical address.

17.2Contiguous Memory Allocation

The simplest scheme: each process occupies one single contiguous block of memory. Memory is divided into a fixed OS partition and a user partition, which is further split among processes using algorithms such as:

StrategyRuleDownside
First FitAllocate the first hole big enoughFast, but leaves small unusable fragments near the front
Best FitAllocate the smallest hole that's still big enoughMinimizes leftover space per allocation, but creates many tiny useless holes
Worst FitAllocate the largest available holeLeaves the biggest possible leftover chunk, but tends to waste large holes fastest

17.3Fragmentation

External Fragmentation

Free memory exists but is split into many small non-contiguous holes, none big enough to satisfy a request — total free space can be plenty, yet unusable. Solved by compaction (shuffling processes together) or moving away from contiguous allocation entirely (paging).

Internal Fragmentation

Allocated memory is slightly larger than requested (e.g. rounded up to a fixed block/page size) — the wasted space is "inside" the allocation and can't be given to anyone else.

Memory Management · 18

Paging

Paging eliminates external fragmentation entirely by allowing a process's physical memory to be non-contiguous — memory is divided into fixed-size frames, and a process's logical address space into equal-size pages.

18.1How address translation works

A logical address splits into a page number (p) and a page offset (d). The page number indexes into a per-process page table, which stores the physical frame number that page currently occupies; the offset is unchanged, since frames and pages are the same size.

address_translation.pseudo
logical_address = (p, d)
frame_number    = page_table[p]
physical_address = (frame_number, d)   // offset d is reused unchanged

18.2Translation Lookaside Buffer (TLB)

Because a page table lookup means an extra memory access for every reference, hardware caches recent (page → frame) translations in a small, fast associative cache — the TLB. A TLB hit skips the page-table walk entirely; a TLB miss falls back to walking the table (and caches the result for next time). TLB hit ratio is one of the most important levers on effective memory access time.

Effective Access Time (EAT): EAT = hit_ratio × (TLB access + memory access) + (1 − hit_ratio) × (TLB access + 2 × memory access) — a miss costs an extra full memory access to walk the page table.

18.3Multilevel & Inverted Page Tables

Hierarchical (Multilevel) Paging

A single-level page table for a 64-bit address space would be absurdly large. Multilevel paging pages the page table itself, so unused regions of the address space cost nothing.

Inverted Page Table

One global table with one entry per physical frame (not per virtual page) — saves huge amounts of memory when address spaces are large, at the cost of slower lookups (often mitigated with a hash table).

Memory Management · 19

Segmentation

Segmentation gives memory a structure that matches how programmers actually think about a program: as a collection of variable-sized logical units — code, stack, heap, a symbol table — rather than uniform fixed-size pages.

19.1How it works

A logical address is a pair (segment number, offset). A segment table maps each segment to a (base, limit) pair in physical memory — base is where the segment starts, limit is its length, letting the hardware bounds-check every reference.

PagingSegmentation
Unit sizeFixedVariable, matches logical program structure
FragmentationInternal onlyExternal (segments of varying sizes leave holes)
Visible to programmer?No, transparentCan be, aids protection/sharing at a logical level

Most real systems (x86 in its modern usage, for instance) combine the two: segmented paging, where each segment is itself paged, getting fragmentation control from paging and logical structure from segmentation.

Memory Management · 20

Virtual Memory & Demand Paging

Virtual memory lets a process run with only part of its address space in physical RAM — separating the logical memory a program sees from the (smaller) physical memory actually installed.

20.1Demand Paging

Pages are loaded into memory only when referenced, not all up-front. Each page-table entry has a valid/invalid bit: valid means the page is in memory; invalid means it either isn't yet, or isn't part of the process's address space at all.

Process references a page marked invalid

The MMU traps to the kernel — this trap is called a page fault.

Kernel checks if the reference is legal

If it's outside the process's valid address space, the process is terminated (segmentation fault).

Find a free frame

If none is free, a page-replacement algorithm picks a victim page to evict (see next section).

Read the needed page from disk into the frame

This is the slow part — disk I/O takes orders of magnitude longer than a memory access.

Update the page table & restart the instruction

The valid bit is set, and the instruction that faulted is re-executed from scratch — it will now succeed.

Copy-on-Write (COW): when fork() creates a child process, instead of copying the whole address space immediately, parent and child initially share the same physical pages marked read-only. Only when either tries to write to a shared page does the kernel copy it — a huge optimization since most children immediately exec() a new program anyway.
Memory Management · 21

Page Replacement Algorithms

When memory is full and a new page must be brought in, a page-replacement algorithm decides which resident page to evict. The goal: minimize the page fault rate.

FIFO — First In, First Out

Evict the page that has been in memory the longest, regardless of how recently it was used. Simple, but suffers from Belady's Anomaly — counterintuitively, adding more frames can sometimes increase the fault count.

Optimal (OPT / MIN)

Evict the page that won't be used for the longest time in the future. Provably minimizes faults — but requires knowing the future reference string, so it's used only as a theoretical benchmark to compare other algorithms against.

LRU — Least Recently Used

Evict the page that hasn't been referenced for the longest time, using the past as an approximation of the future. Performs close to optimal in practice, but needs hardware support (timestamps or a reference stack) to track recency cheaply.

LFU — Least Frequently Used

Evict the page with the smallest reference count. Can wrongly keep a page that was heavily used long ago but is now cold — often paired with aging/decay to fix this.

Memory Management · 22

Thrashing & the Working Set Model

Thrashing is what happens when the system spends more time paging (servicing page faults) than executing actual instructions — CPU utilization collapses even though every process is technically "running."

22.1How thrashing spirals

Too many processes, too little memory per process

Each process doesn't have enough frames to hold its actively-used pages.

Page fault rate rises

Processes constantly fault, waiting on slow disk I/O instead of computing.

CPU utilization drops

The OS scheduler sees low CPU utilization and — mistakenly reading this as "not enough multiprogramming" — admits more processes.

The spiral worsens

More processes means even less memory per process, even more faults, even lower CPU utilization. Without intervention this feedback loop collapses the system.

22.2The Working Set Model

The working set of a process is the set of pages it has referenced in the most recent Δ time units — an approximation of the pages it "actively needs" right now. If the sum of all processes' working sets exceeds total available frames, the medium-term scheduler should swap a process out entirely rather than let everyone starve for frames simultaneously.

Page-Fault Frequency (PFF): a simpler, reactive alternative — monitor each process's fault rate directly; if it's too high, give that process more frames; if too low, take some away and give them to a process that needs them more.
Storage & File Systems · 23

File Concepts

A file is the OS's abstraction for persistent storage — a named collection of related information, insulating programs from the physical properties of the storage device underneath.

23.1File Attributes

NameIdentifier (inode #)TypeLocation on disk SizeProtection bitsTimestampsOwner / group

23.2File Operations

The core set every file system supports: create, open, read, write, seek (reposition within the file), close, delete, and truncate. The OS maintains an open-file table so repeated reads/writes don't need to re-specify the file each time — just a file descriptor / handle.

23.3Access Methods

Sequential Access

Read/write proceeds in order from the beginning — the simplest and most common method, natural fit for tape and streaming.

Direct (Random) Access

A file is viewed as numbered fixed-length blocks/records that can be read or written in any order — essential for databases.

Indexed Access

An index (built on top of direct access) maps keys to block numbers, enabling fast lookup without scanning — how database engines locate records efficiently.

Storage & File Systems · 24

Directory Structures

Directories organize the namespace of files — they're themselves usually just special files containing (name → metadata/location) mappings.

Single-Level Directory

One directory for the entire file system. Simple but every file needs a unique name system-wide — unworkable beyond a handful of files or users.

Two-Level Directory

Each user gets their own directory. Solves naming collisions between users, but users still can't share files easily and can't organize their own files into sub-groups.

Tree-Structured Directory

Directories can contain subdirectories to any depth — the familiar model in every modern OS. Introduces the idea of a current working directory and both absolute and relative paths.

Acyclic-Graph Directory

Allows shared subdirectories/files via links (hard links, symbolic links) — the same file can appear in multiple directories, but cycles are still forbidden to keep traversal well-defined.

General Graph Directory

Allows arbitrary cycles. Powerful but requires garbage collection or reference counting to know when a file with multiple links can truly be deleted, and cycle detection to avoid infinite traversal loops.

File Allocation Methods

How does the file system decide which disk blocks belong to which file, and in what order?

Contiguous Each file occupies a set of consecutive blocks Excellent sequential and direct access; minimal seek overhead External fragmentation; hard to grow a file in place

Storage & File Systems · 26

Free Space Management

The file system must track which blocks are free to hand out for new files or extensions.

Bit Vector (Bitmap)

One bit per block: 1 = free, 0 = allocated (or vice versa). Compact and fast to scan for runs of free contiguous blocks.

Linked List

Free blocks are chained together in a list; no wasted space computing a bitmap, but finding a large contiguous run is slow.

Grouping

The first free block stores addresses of several other free blocks — an optimization over a plain linked list that reduces traversal length.

Counting

Since free blocks are often contiguous in practice, store (starting block, count of free blocks following it) pairs instead of one entry per block.

Storage & File Systems · 27

Disk Scheduling Algorithms

On spinning disks, moving the read/write head (seeking) is the slowest operation by far. Disk scheduling decides the order to service pending I/O requests to minimize total head movement — still relevant conceptually even on SSDs, where the analogous goal shifts to command queuing and wear-leveling.

FCFS

Service requests in the order they arrive. Fair, but ignores head position entirely — can cause wild, wasteful back-and-forth seeking.

SSTF — Shortest Seek Time First

Always service the request closest to the current head position. Minimizes seek time locally, but can starve requests far from the "hot" area of the disk.

SCAN (Elevator Algorithm)

The head sweeps in one direction servicing all requests along the way, then reverses at the end — exactly like an elevator visiting every floor requested along its current direction.

C-SCAN — Circular SCAN

Like SCAN, but after reaching one end, the head jumps back to the beginning without servicing on the return trip — gives more uniform wait times since it treats the disk as circular.

LOOK & C-LOOK

Same idea as SCAN/C-SCAN, but the head only travels as far as the last request in each direction, instead of always going all the way to the disk's physical edge — avoiding wasted travel over empty regions.

Keeps a copy of frequently-used data in faster storage to avoid re-fetching from a slower source.

Spooling

Queues output for a device that can only serve one job at a time (classically, a printer), so multiple processes can "print" without waiting on the physical device directly.

I/O & Protection · 30

Protection

Protection is the mechanism for controlling access to system resources — separate from security (below), which is about deciding policy: who should be allowed to do what in the first place.

30.1Domain of Protection

A protection domain defines the set of (object, access rights) pairs a process may use at a given time — e.g. a domain might allow read/write on file.txt but only execute on a specific binary. Processes can switch domains (e.g. a user process gaining kernel-domain rights during a system call).

30.2Access Matrix

A conceptual table with domains as rows and objects as columns; each cell lists the operations that domain may perform on that object. In practice it's implemented sparsely, since most cells are empty:

Access Control List (ACL)

Store the matrix by column — each object keeps a list of (domain, rights) pairs. "Who can access this file, and how?" — what UNIX permission bits and Windows ACLs both implement.

Capability List

Store the matrix by row — each domain/process holds a list of the objects it may access along with its rights, like a keyring of unforgeable tickets. "What can this process touch?"

30.3The Principle of Least Privilege

Every process, user, and program should operate with the minimum set of rights necessary to accomplish its task, and nothing more — dramatically limiting the blast radius if that process is ever compromised.

Virtualization & Hypervisors

Virtualization lets one physical machine run multiple independent, isolated "virtual machines" (VMs), each believing it has its own dedicated hardware.

35.1Hypervisor Types

TYPE 1

Bare-Metal Hypervisor

Runs directly on the physical hardware, with no host OS underneath — it is the lowest software layer. Better performance and isolation; used in datacenters. Examples: VMware ESXi, Microsoft Hyper-V, Xen, KVM (technically a kernel module turning Linux itself into a Type-1 hypervisor).

TYPE 2

Hosted Hypervisor

Runs as an application on top of a conventional host OS. Simpler to set up for desktop use, but adds a layer of overhead versus Type 1. Examples: VirtualBox, VMware Workstation/Fusion, Parallels.

35.2How CPU virtualization works

Modern CPUs (Intel VT-x, AMD-V) provide hardware-assisted virtualization: a new, more-privileged mode lets the hypervisor trap and emulate sensitive instructions the guest OS tries to execute, without the guest needing to be modified at all (full virtualization). Older/software-only approaches used paravirtualization (the guest OS is modified to cooperate with the hypervisor) or full binary translation.

Why it matters: virtualization is the foundation of cloud computing — AWS, Azure, and GCP sell you slices of physical servers as VMs, letting many customers securely share hardware they'll never see.

Advanced & Modern OS · 37

Distributed Systems Concepts

A distributed system is a collection of independent computers that appears to its users as a single coherent system — the OS-level concepts here generalize scheduling, synchronization, and memory management across a network instead of within one machine.

37.1Core challenges

No global clock

Different machines' clocks drift; "simultaneous" events need logical clocks (Lamport timestamps, vector clocks) instead of wall-clock time.

Partial failure

Unlike a single machine that's either up or down, a distributed system can have some nodes fail while others keep working — software must be designed to expect and tolerate this.

Network unreliability

Messages can be delayed, lost, duplicated, or reordered — the system must be correct even under these conditions.

Consistency vs. availability

The CAP theorem: under a network partition, a distributed data store must choose between staying Consistent or staying Available — it can't guarantee both.

37.2Distributed coordination building blocks

  • Distributed mutual exclusion — extending the critical-section problem across machines with no shared memory (e.g. token-passing, quorum-based algorithms).
  • Consensus — getting a set of nodes to agree on a single value even if some fail (Paxos, Raft) — the backbone of distributed databases and leader election.
  • Distributed file systems — presenting files stored across many machines under one namespace (NFS, HDFS, Google File System).
  • Load balancing & replication — spreading requests and duplicating data across nodes for both performance and fault tolerance.

Real-Time Operating Systems — Deep Dive

RTOS design revisits nearly every concept in this guide with one added constraint: correctness includes timing, not just logical results.

39.1Real-time scheduling algorithms

Rate Monotonic Scheduling (RMS)

Static priorities assigned by task period — shorter period means higher priority. Simple and provably optimal among static-priority algorithms, provided total CPU utilization stays under a calculable bound (~69% for many tasks).

Earliest Deadline First (EDF)

Dynamic priority: whichever ready task has the nearest deadline runs next. Can achieve up to 100% CPU utilization in theory — optimal, but more complex to implement and reason about than RMS.

39.2Priority Inversion

A dangerous scenario: a low-priority task holds a lock a high-priority task needs, and an unrelated medium-priority task preempts the low-priority one — effectively blocking the high-priority task indefinitely. Famously nearly doomed the Mars Pathfinder mission in 1997. Fixed with priority inheritance (temporarily boost the lock-holder's priority to that of the task waiting on it) or priority ceiling protocols.

40.1What a device driver does

A driver translates a device-independent OS request ("write these bytes") into the exact register writes, command sequences, and interrupt handling a specific piece of hardware requires — presenting a uniform interface upward while hiding wild diversity downward.

    return 0;
}

static void __exit hello_exit(void) {
    printk(KERN_INFO "hello_module: unloaded\n");
}

module_init(hello_init);
module_exit(hello_exit);
MODULE_LICENSE("GPL");
Kernel code runs with full hardware privilege and no safety net — a bug here can crash or corrupt the entire machine, unlike a bug in a user-space app. This is exactly why microkernels (Section 04) push drivers out of kernel space where possible.

40.2Character vs. Block Devices

Character Devices

Data transferred as a stream of bytes, no fixed structure — keyboards, mice, serial ports.

Block Devices

Data transferred in fixed-size blocks, randomly addressable — hard disks, SSDs, USB drives.

Learning Path · 41

Beginner → Advanced OS Learning Roadmap

A practical order to actually learn this material — reading a textbook cover to cover is one path, but building things alongside it cements every concept far better.

STAGE 1 · Weeks 1–3

Foundations & Everyday Fluency

Understand what an OS does (Sections 1–6). In parallel, get genuinely comfortable at a Linux command line (Section 33) — install a distro in a VM if you're not already on one, and use the terminal for daily tasks instead of a GUI.

STAGE 2 · Weeks 4–7

Processes, Threads & Scheduling

Study process states, the PCB, and every CPU scheduling algorithm (Sections 7–11) — work through Gantt charts by hand, then verify with the simulator above. Write a small multithreaded program (Section 10's pthreads example is a good starting point) and observe real race conditions before you "fix" them.

STAGE 3 · Weeks 8–11

Synchronization & Deadlock

Implement producer-consumer with real semaphores in C or Python. Trace through the Dining Philosophers deadlock by hand, then fix it three different ways. Run the Banker's Algorithm simulator on scenarios you construct yourself until "safe state" clicks intuitively.

STAGE 4 · Weeks 12–16

Memory & Storage

Paging and virtual memory (Sections 17–22) are the hardest conceptual jump in the whole subject — budget real time here. Trace page-fault sequences by hand before trusting the simulator. Then move to file systems and disk scheduling (23–28), ideally reading how a real filesystem like ext4 lays out inodes.

STAGE 5 · Weeks 17–20

Build a Toy OS Component

This is where theory becomes real. Follow the xv6 or OSTEP projects (Section 42) to implement a basic scheduler, a simple shell, or a minimal file system yourself in a teaching kernel — nothing cements this material like debugging your own page fault handler at 1am.

STAGE 6 · Ongoing

Modern & Advanced Systems

Layer on virtualization, containers, and distributed systems (Sections 35–39) — spin up Docker containers and inspect their namespaces/cgroups directly with unshare and systemd-cgtop. Read a real kernel's scheduler source (Linux's CFS) once the textbook algorithms feel natural.

A–Z Glossary of OS Terms

Quick-reference definitions for every core term used across this guide.

Address Binding
Mapping symbolic program addresses to actual memory addresses, done at compile, load, or execution time.
Belady's Anomaly
The counterintuitive case where adding more page frames increases (rather than decreases) the number of page faults under FIFO replacement.
Bootloader
The small program that loads the OS kernel into memory during startup.
Cgroups
Linux kernel feature that limits and accounts for resource usage (CPU, memory, I/O) of a group of processes.
Context Switch
Saving one process's CPU state and loading another's so the CPU can switch which process it executes.
Deadlock
A state where a set of processes are each blocked waiting for a resource held by another in the set, forever.
Demand Paging
Loading pages into memory only when they're actually referenced, not all at process start.
External Fragmentation
Free memory split into scattered small holes that together could satisfy a request, but individually can't.
Fork
The UNIX system call that creates a new process by duplicating the calling process.
Hypervisor
Software that creates and manages virtual machines, either running directly on hardware (Type 1) or atop a host OS (Type 2).
Internal Fragmentation
Wasted space inside an allocated block because the allocation is larger than what was actually requested.
Interrupt
A signal to the CPU indicating an event needs immediate attention, causing it to suspend current execution and run a handler.
Kernel
The core of the OS that has full hardware access and runs at the highest privilege level.
Livelock
Processes keep changing state in response to each other but none makes actual progress — unlike deadlock, they're not blocked, just stuck looping.
Monitor
A high-level synchronization construct bundling shared data with the only procedures allowed to touch it, with mutual exclusion enforced automatically.
Mutex
A lock allowing only one thread to hold it at a time, used to protect a critical section.
Namespace
A Linux kernel feature giving a process an isolated view of a global resource (PIDs, network, mounts), foundational to containers.
Page Fault
A trap raised when a program references a page that is not currently loaded in physical memory.
Page Table
The per-process data structure mapping virtual page numbers to physical frame numbers.
PCB (Process Control Block)
The kernel data structure holding all the state needed to suspend and later resume a process.
Preemption
Forcibly taking the CPU (or a resource) away from a process before it voluntarily gives it up.
Race Condition
A bug where the outcome depends on the unpredictable relative timing of concurrent operations on shared data.
Semaphore
An integer synchronization variable manipulated only via atomic wait()/signal() operations.
Starvation
A process waits indefinitely for a resource because other processes keep being favored ahead of it — the system as a whole still progresses.
Swapping
Moving an entire process between memory and disk to free up RAM for other processes.
Thrashing
A state where the system spends more time paging than executing real instructions, collapsing CPU utilization.
Thread
An independent unit of execution within a process, sharing the process's memory and resources with other threads.
TLB (Translation Lookaside Buffer)
A fast hardware cache of recent virtual-to-physical address translations.
Trap
A software-generated interrupt, typically caused by an error or a deliberate system call request.
Virtual Memory
An abstraction giving each process the illusion of a large, contiguous, private address space, backed by a mix of physical RAM and disk.
Working Set
The set of pages a process has referenced within its most recent window of execution — an estimate of what it "actively needs" in memory right now.
Zombie Process
A terminated process whose exit status hasn't yet been collected by its parent, so its PCB/entry lingers in the process table.
