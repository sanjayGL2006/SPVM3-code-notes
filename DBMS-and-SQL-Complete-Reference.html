A

Foundations of DBMS

What a database management system is, why it replaced file systems, and how it's architected.
01CORE

What is a DBMS?

Definition: A Database Management System (DBMS) is software that creates, stores, manages, and controls access to data in a database — a structured, persistent collection of related data. It sits between applications and the physical data, offering a controlled interface instead of direct file access.

A DBMS provides four core guarantees: data definition (schemas), data manipulation (query/update), data control (security/permissions), and data integrity (constraints, transactions).

Examples: MySQL, PostgreSQL, Oracle Database, SQL Server, SQLite, MongoDB. The first four are relational DBMS (RDBMS) — the focus of this guide.
02CORE

File System vs DBMS

Before DBMS became standard, applications stored data directly in OS files. This caused problems a DBMS is specifically designed to solve.

Problem in File SystemsHow DBMS Solves It
Data redundancy & inconsistencyCentralized storage, normalization
Difficult concurrent accessConcurrency control (locking, MVCC)
No atomicity on crashesTransactions & recovery (ACID)
No standard query languageSQL as a declarative interface
Weak securityUser roles, GRANT/REVOKE (DCL)
Rigid, hard-to-change structureData independence (logical/physical)
03CORE

DBMS Architecture

1-Tier: the database is directly accessible to the user on the same machine (e.g. local SQLite file) — used mainly for development.

2-Tier (Client-Server): a client application talks directly to the database server over a network, e.g. a desktop app connecting straight to MySQL.

3-Tier: a middle application/logic tier sits between the client and the database, so clients never talk to the DB directly. This is the standard architecture for web applications (browser → app server → database).

ANSI-SPARC 3-level schema architecture (a separate but related idea): External level (user views) → Conceptual level (logical schema, tables/relationships) → Internal level (physical storage, indexes, files). This layering is what enables data independence (below).

This guide focuses on the Relational Model, which is designed on paper using the Entity-Relationship (ER) Model below.

06CORE

Entity-Relationship Model

Definition: A conceptual design tool that represents data as entities (real-world objects, e.g. Employee), their attributes (properties, e.g. name, salary), and relationships between entities (e.g. Employee works in Department).

Entity types: a strong entity has its own primary key (e.g. Employee); a weak entity depends on another entity for identification (e.g. Dependent, identified only along with an Employee).

Attribute types: simple, composite (Name → First + Last), single-valued, multi-valued (PhoneNumbers), derived (Age, from DateOfBirth).

07CORE

ER Diagram Notation & Cardinality

Standard shapes: rectangles = entities, ellipses = attributes, diamonds = relationships, double rectangles = weak entities.

Cardinality describes how many instances of one entity relate to another:

CardinalityMeaningExample
1 : 1One entity relates to exactly one of anotherEmployee ↔ Parking Spot
1 : NOne relates to manyDepartment → Employees
M : NMany relate to manyStudents ↔ Courses
Participation: total participation (double line) means every instance must participate in the relationship; partial (single line) means participation is optional.
08CORE

Generalization, Specialization & Aggregation

Generalization: bottom-up — combine common attributes of multiple lower-level entities into a higher-level entity (Car + Truck → Vehicle).

Specialization: top-down — split a higher-level entity into specialized sub-entities (Employee → Manager, Engineer).

Aggregation: treats a relationship itself as a higher-level entity, so it can participate in further relationships (e.g. "Employee works-on Project", as a whole, is Monitored-by a Manager).

09CORE

Mapping ER to Relational Schema

Rules for converting an ER diagram into tables:

MAPPING RULES
1. Strong entity → its own table, key attribute = primary key 2. Weak entity → table with FK to owner + partial key = composite PK 3. 1:1 relationship → FK on either side (often the side with total participation) 4. 1:N relationship → FK placed on the "many" side 5. M:N relationship → new junction/bridge table holding both FKs 6. Multi-valued attr. → separate table referencing the owning entity's PK
Example: Students ↔ Courses (M:N) becomes three tables — students, courses, and a junction table enrollments(student_id, course_id, grade).

Relational Model & Keys

The mathematical foundation of tables, rows, and the keys that uniquely identify and connect them.
10CORE

11CORE

Candidate, Primary, Super & Alternate Keys

Super Key: any set of attributes that can uniquely identify a tuple (may contain extra, unnecessary attributes).

Candidate Key: a minimal super key — no attribute can be removed without losing uniqueness. A table can have several.

Primary Key: the candidate key chosen to be the table's main identifier. Cannot be NULL, must be unique.

Alternate Key: any candidate key not chosen as primary key.

12CORE

Foreign Key & Referential Integrity

Definition: A foreign key is an attribute (or set of attributes) in one table that references the primary key of another table, linking the two relations.

SYNTAX
CREATE TABLE employees ( emp_id INT PRIMARY KEY, dept_id INT, FOREIGN KEY (dept_id) REFERENCES departments(dept_id) );

Referential integrity is the rule this enforces: a foreign key value must either match an existing primary key value in the referenced table, or be NULL. Databases reject inserts/updates that would violate this — and by default reject deleting a referenced parent row.

13CORE

Composite & Surrogate Keys

Composite key: a primary key made of two or more columns together, e.g. enrollments(student_id, course_id) — neither column alone is unique, but the pair is.

Surrogate key: an artificial key with no business meaning, generated purely for identification — typically an auto-incrementing integer or UUID (e.g. emp_id), used instead of a natural/business key that might change over time.

16CORE

Join & Division Operations

⋈ (Natural Join / Theta Join): combines two relations on a matching condition — the algebraic origin of every SQL JOIN.

employees ⋈ employees.dept_id = departments.dept_id departments

÷ (Division): finds tuples in A that are associated with all tuples in B — e.g. "find students enrolled in every course a department offers." SQL expresses this with nested NOT EXISTS rather than a direct operator.

17CORE

Relational Algebra vs SQL

Relational algebra is procedural — you specify the sequence of operations. SQL is declarative — you specify what you want, and the DBMS's query optimizer decides the actual execution plan (often re-ordering operations for performance, e.g. pushing selections before joins).

Relational calculus (tuple & domain calculus) is the declarative theoretical counterpart — SQL's SELECT syntax is closer in spirit to calculus, while its evaluation follows algebra.

SQL Fundamentals

Structured Query Language, in full — every statement type, with runnable examples.
18CORE

Introduction to SQL & Its Categories

SQL (Structured Query Language) is the standard declarative language for relational databases. It is used identically in spirit — though with dialect differences — across MySQL, PostgreSQL, Oracle, SQL Server, and SQLite (each covered in its own companion guide in this series).

SQL splits into five categories, each covered as its own concept below:

DDL — CREATE, ALTER, DROP, TRUNCATE (structure) DML — INSERT, UPDATE, DELETE (data) DQL — SELECT (retrieval) DCL — GRANT, REVOKE (permissions) TCL — COMMIT, ROLLBACK, SAVEPOINT (transactions)
19DDL

DDL — CREATE, ALTER, DROP, TRUNCATE

Data Definition Language statements define and modify the structure of the database — they are auto-committed in most RDBMS (cannot be rolled back).

SYNTAX
CREATE TABLE table_name (col1 TYPE constraints, col2 TYPE constraints, ...); ALTER TABLE table_name ADD COLUMN col_name TYPE; ALTER TABLE table_name DROP COLUMN col_name; DROP TABLE table_name; TRUNCATE TABLE table_name; -- removes all rows, keeps structure
ddl_demo.sql
DROP deletes the table and its data permanently; TRUNCATE empties the table but keeps its schema; DELETE (DML) removes rows one at a time and can be rolled back.
20DML

DML — INSERT, UPDATE, DELETE

Data Manipulation Language statements change the contents of tables. Unlike DDL, these are transactional and can be rolled back before COMMIT.

SYNTAX
INSERT INTO table_name (col1, col2) VALUES (val1, val2); UPDATE table_name SET col1 = val1 WHERE condition; DELETE FROM table_name WHERE condition;
dml_demo.sql
Always pair UPDATE/DELETE with WHERE. Omitting WHERE updates or deletes every row in the table.
21DQL

DQL — SELECT, WHERE, ORDER BY, LIMIT

SYNTAX
SELECT column1, column2, ... FROM table_name WHERE condition ORDER BY column [ASC|DESC] LIMIT n;
select_demo.sql
22DCL

DCL — GRANT, REVOKE

Data Control Language manages who can do what. Access control operates on database objects (tables, views, schemas) and specific privilege types.

SYNTAX
GRANT SELECT, INSERT ON employees TO analyst_role; REVOKE INSERT ON employees FROM analyst_role; GRANT ALL PRIVILEGES ON database_name.* TO 'admin'@'localhost';
DCL is not part of the in-browser playground (it requires real user/role infrastructure), but the syntax above is standard across MySQL, PostgreSQL, and Oracle.
23TCL

TCL — COMMIT, ROLLBACK, SAVEPOINT

Transaction Control Language marks the boundaries of a transaction — a group of DML statements that succeed or fail together (see Module I for full ACID coverage).

SYNTAX
BEGIN TRANSACTION; UPDATE accounts SET balance = balance - 500 WHERE acct_id = 1; SAVEPOINT after_debit; UPDATE accounts SET balance = balance + 500 WHERE acct_id = 2; COMMIT; -- makes changes permanent -- or: ROLLBACK TO after_debit; -- undo back to a savepoint ROLLBACK; -- undo the entire transaction

25DQL

Aggregate Functions, GROUP BY & HAVING

Aggregate functions collapse many rows into one summary value: COUNT(), SUM(), AVG(), MIN(), MAX(). GROUP BY applies them per group instead of the whole table. HAVING filters groups after aggregation (WHERE filters rows before).

SYNTAX
SELECT dept_id, COUNT(*) AS emp_count, AVG(salary) AS avg_salary FROM employees GROUP BY dept_id HAVING COUNT(*) > 1 ORDER BY avg_salary DESC;
group_by_demo.sql
Rule: every non-aggregated column in SELECT must appear in GROUP BY.

Joins, subqueries, views, indexes, window functions, and CTEs — where real-world querying lives.
26DQL

Joins — INNER, LEFT, RIGHT, FULL

Joins combine rows from two or more tables based on a related column.

JoinReturns
INNER JOINOnly rows with a match in both tables
LEFT JOINAll left rows + matches from right (NULL if none)
RIGHT JOINAll right rows + matches from left (NULL if none)
FULL OUTER JOINAll rows from both sides, matched where possible
SELECT e.name, d.dept_name FROM employees e INNER JOIN departments d ON e.dept_id = d.dept_id;

27DQL

Self, Cross & Natural Joins

Self Join: a table joined to itself — typically for hierarchical data like employee → manager.

SELECT e.name AS employee, m.name AS manager FROM employees e JOIN employees m ON e.manager_id = m.emp_id;

Cross Join: the Cartesian product — every row of A paired with every row of B (no ON clause). Rarely used directly except to generate combinations.

Natural Join: automatically joins on all identically-named columns in both tables — convenient but risky if column names collide unintentionally. Most style guides recommend explicit ON conditions instead.

28DQL

Subqueries — Scalar, Nested & Correlated

Scalar subquery: returns a single value, usable anywhere a value is expected.

Nested (IN) subquery: returns a list, used with IN/NOT IN.

Correlated subquery: references a column from the outer query, so it re-runs once per outer row — powerful but can be slow on large tables.

29DQL

Set Operations — UNION, INTERSECT, EXCEPT

OperatorReturns
UNIONRows from either query, duplicates removed
UNION ALLRows from either query, duplicates kept (faster)
INTERSECTRows present in both queries
EXCEPT / MINUSRows in the first query but not the second

30DDL

Views

Definition: A view is a saved, named SELECT query that behaves like a virtual table. It doesn't store data itself (unless materialized) — it re-runs its defining query each time it's referenced.

SYNTAX
CREATE VIEW high_earners AS SELECT name, salary, dept_id FROM employees WHERE salary > 65000; SELECT * FROM high_earners; -- queried just like a table DROP VIEW high_earners;

Views simplify complex recurring queries, restrict column/row access for security, and provide a stable interface even if underlying tables change.

31DDL

Indexes in SQL

An index is an auxiliary structure that speeds up lookups on a column, at the cost of extra storage and slower writes (the index must be updated on every INSERT/UPDATE/DELETE).

SYNTAX
CREATE INDEX idx_emp_salary ON employees(salary); CREATE UNIQUE INDEX idx_emp_email ON employees(email); DROP INDEX idx_emp_salary;
Primary keys and UNIQUE constraints automatically create an index. See Module J for the internal B-Tree/hash structures that make indexes fast.
32DQL

Window Functions

Unlike GROUP BY (which collapses rows), window functions compute a value across a set of related rows while keeping every row in the output.

SELECT name, dept_id, salary, RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rank_in_dept, AVG(salary) OVER (PARTITION BY dept_id) AS dept_avg, ROW_NUMBER() OVER (ORDER BY salary DESC) AS overall_rank FROM employees;
FunctionBehavior
ROW_NUMBER()Sequential number, no ties
RANK()Same rank for ties, gaps after
DENSE_RANK()Same rank for ties, no gaps
LAG() / LEAD()Value from a previous/next row
Window functions aren't executed by this page's playground engine (they need real per-partition state) — the syntax above is standard across PostgreSQL, MySQL 8+, and Oracle.
33DQL

Common Table Expressions (CTE) & Recursive Queries

A CTE is a named, temporary result set defined with WITH, scoped to a single query — it makes complex queries readable by breaking them into named steps.

WITH dept_totals AS ( SELECT dept_id, SUM(salary) AS total_salary FROM employees GROUP BY dept_id ) SELECT d.dept_name, t.total_salary FROM dept_totals t JOIN departments d ON t.dept_id = d.dept_id; -- Recursive CTE (e.g. organization chart): WITH RECURSIVE org_chart AS ( SELECT emp_id, name, manager_id, 1 AS level FROM employees WHERE manager_id IS NULL UNION ALL SELECT e.emp_id, e.name, e.manager_id, oc.level + 1 FROM employees e JOIN org_chart oc ON e.manager_id = oc.emp_id ) SELECT * FROM org_chart;
G

Stored Programs (PL/SQL style)

Procedural extensions to SQL — logic that lives inside the database itself. Full dialect-specific syntax is in the companion PL/SQL guide.
34CORE

Stored Procedures

A stored procedure is a named, precompiled block of procedural SQL stored in the database and invoked by name — useful for encapsulating multi-step business logic close to the data.

SYNTAX (generic / PL-SQL style)
CREATE PROCEDURE give_raise(IN p_emp_id INT, IN p_amount DECIMAL) BEGIN UPDATE employees SET salary = salary + p_amount WHERE emp_id = p_emp_id; END; CALL give_raise(3, 5000);
Procedures can take IN, OUT, and INOUT parameters, and don't necessarily return a value — that's the key difference from functions.
35CORE

User-Defined Functions

A function is a stored routine that always returns a value and can be used inline inside a SQL statement (e.g. in a SELECT list), unlike a procedure.

CREATE FUNCTION annual_salary(monthly DECIMAL) RETURNS DECIMAL BEGIN RETURN monthly * 12; END; SELECT name, annual_salary(salary/12) FROM employees;
36CORE

Triggers

A trigger is code that runs automatically before or after an INSERT, UPDATE, or DELETE on a table — used for auditing, enforcing complex rules, or keeping denormalized data in sync.

CREATE TRIGGER trg_salary_audit AFTER UPDATE ON employees FOR EACH ROW BEGIN INSERT INTO salary_audit(emp_id, old_salary, new_salary, changed_at) VALUES (OLD.emp_id, OLD.salary, NEW.salary, NOW()); END;
OLD and NEW refer to the row's values before and after the change. Triggers are powerful but can make data flow hard to trace — use sparingly.
37CORE

Cursors

A cursor lets procedural code step through a result set row by row — necessary when a task can't be expressed as one set-based SQL statement.

DECLARE emp_cursor CURSOR FOR SELECT emp_id, salary FROM employees; DECLARE v_id INT; DECLARE v_sal DECIMAL; OPEN emp_cursor; FETCH emp_cursor INTO v_id, v_sal; WHILE FOUND DO UPDATE employees SET salary = v_sal * 1.05 WHERE emp_id = v_id; FETCH emp_cursor INTO v_id, v_sal; END WHILE; CLOSE emp_cursor;
Cursors are slower than a single set-based UPDATE — prefer set-based SQL whenever the logic allows it; reach for cursors only when row-by-row procedural logic is genuinely required.
38CORE

Exception Handling

Procedural SQL blocks can catch and handle runtime errors instead of letting them abort silently.

BEGIN INSERT INTO employees(emp_id, name) VALUES (1, 'Duplicate'); EXCEPTION WHEN unique_violation THEN RAISE NOTICE 'Employee ID already exists, skipping insert.'; WHEN OTHERS THEN RAISE NOTICE 'Unexpected error occurred.'; END;
H

Normalization & Design

Eliminating redundancy and anomalies by systematically restructuring tables.
39CORE

Functional Dependencies

Definition: An attribute B is functionally dependent on attribute A (written A → B) if each value of A is associated with exactly one value of B. Functional dependencies are the formal basis for every normal form.

emp_id → name, salary, dept_id -- emp_id determines everything about the employee dept_id → dept_name, location -- a partial dependency risk if mixed into employees table

Trivial FD: B is a subset of A (always true, not useful). Partial FD: a non-key attribute depends on only part of a composite key. Transitive FD: A → B and B → C implies A → C indirectly.

40CORE

First Normal Form (1NF)

Rule: every column must hold atomic (indivisible) values, and each row must be unique — no repeating groups or multi-valued columns.

41CORE

Second & Third Normal Form (2NF, 3NF)

2NF: must be in 1NF, and every non-key attribute must depend on the entire primary key — no partial dependency on part of a composite key.

3NF: must be in 2NF, and no non-key attribute may depend transitively on the key through another non-key attribute (every non-key column depends on "the key, the whole key, and nothing but the key").

42CORE

Boyce-Codd Normal Form (BCNF)

Rule: a stricter version of 3NF — for every functional dependency A → B, A must be a super key. BCNF resolves rare anomalies that 3NF allows when a table has multiple overlapping candidate keys.

In practice, most well-designed 3NF schemas are already in BCNF. The distinction matters mainly when a table has more than one candidate key that overlaps in columns.
43CORE

4NF & 5NF

4NF: must be in BCNF, and have no multi-valued dependencies — e.g. a table storing (student, language_spoken, sport_played) mixes two independent multi-valued facts about a student and should be split into two tables.

5NF (Project-Join Normal Form): a table should not be reconstructible by joining smaller tables unless that join-decomposition is truly lossless and necessary — resolves rare join-dependency redundancy. Mostly of theoretical interest in everyday schema design.

44CORE

Denormalization

Definition: the deliberate, controlled reintroduction of redundancy into a normalized schema — trading some write-time consistency risk for read-time performance, typically in reporting/analytics systems (data warehouses) where reads vastly outnumber writes.

Common technique: storing a precomputed total_orders count on a customer row instead of always running COUNT() over the orders table.
I

Transactions & Concurrency

How a DBMS keeps data correct when many operations happen at once, and recovers cleanly from crashes.
45CORE

Transactions & ACID Properties

Definition: a transaction is a sequence of one or more operations treated as a single logical unit of work — either all of it happens, or none of it does.

PropertyGuarantee
AtomicityAll operations succeed, or all are rolled back
ConsistencyA transaction moves the DB from one valid state to another, respecting all constraints
IsolationConcurrent transactions don't see each other's incomplete changes
DurabilityOnce committed, changes survive even a crash
-- Classic example: bank transfer BEGIN; UPDATE accounts SET balance = balance - 500 WHERE acct_id = 1; UPDATE accounts SET balance = balance + 500 WHERE acct_id = 2; COMMIT; -- if either UPDATE fails, ROLLBACK undoes both
46CORE

Schedules & Serializability

A schedule is the order in which operations from multiple transactions actually execute. A schedule is serializable if its result is equivalent to some serial (one-at-a-time) execution of the same transactions — the gold standard for correctness under concurrency.

Conflict serializability is checked by building a precedence graph of conflicting operations; if the graph has no cycles, the schedule is conflict-serializable.

47CORE

Concurrency Control — Locking Protocols

Shared (S) lock: allows concurrent reads, blocks writes. Exclusive (X) lock: blocks all other reads and writes.

Two-Phase Locking (2PL): every transaction has a growing phase (acquiring locks) followed by a shrinking phase (releasing locks) — once a lock is released, no new locks can be acquired. This guarantees conflict serializability.

Strict 2PL (used by most real databases) holds all exclusive locks until COMMIT/ROLLBACK, avoiding cascading rollbacks.
48CORE

Timestamp Ordering & MVCC

Timestamp ordering: each transaction gets a unique timestamp at start; conflicting operations are ordered by timestamp instead of locks, aborting/retrying a transaction that would violate the order.

MVCC (Multi-Version Concurrency Control): used by PostgreSQL, MySQL InnoDB, and Oracle — instead of blocking readers, the DB keeps multiple versions of a row, so readers see a consistent snapshot while writers create new versions. This lets reads and writes proceed without blocking each other.

49CORE

Deadlocks — Detection, Prevention & Recovery

Deadlock: two or more transactions each hold a lock the other needs, so none can proceed.

StrategyApproach
PreventionOrder resource acquisition, or use wait-die / wound-wait schemes based on timestamps
DetectionBuild a wait-for graph periodically; a cycle means deadlock
RecoveryAbort one transaction (the "victim") to break the cycle, then retry it

Recovery techniques for crashes rely on the write-ahead log (WAL): changes are logged before being applied, so after a crash the DBMS can redo committed transactions and undo uncommitted ones. Checkpoints periodically flush logged changes to disk to bound recovery time.

J

Storage & Query Optimization

What happens physically on disk, and how the optimizer decides the fastest way to answer a query.
50CORE

Storage Hierarchy & File Organization

Storage hierarchy (fastest/smallest to slowest/largest): CPU registers → cache → main memory (RAM) → SSD/disk → tape/archive. Databases are optimized around the reality that disk access is orders of magnitude slower than memory.

File organizationLayout
Heap (unordered)Rows appended in insertion order — fast inserts, slow search
Sequential (sorted)Rows kept in key order — fast range scans, slower inserts
HashRows placed by a hash of the key — very fast exact-match lookup
ClusteredTable rows physically ordered by an index key (usually the PK)
51CORE

Indexing Structures — B-Tree, B+Tree, Hashing

B-Tree: a balanced, self-sorting tree where every node stores both keys and data pointers — good for point lookups.

B+Tree (used by nearly every RDBMS index): internal nodes store only keys for navigation; all actual data pointers live in leaf nodes, which are linked together — this makes both point lookups and range scans (BETWEEN, ORDER BY) efficient.

Hash index: O(1) average lookup for exact-match equality, but useless for range queries or sorting, since hashing destroys order.

This is why WHERE salary = 50000 can use a hash or B+Tree index equally well, but WHERE salary BETWEEN 40000 AND 60000 needs a B+Tree.
52CORE

Query Processing & Optimization

A SQL query passes through four stages before returning results:

1. Parsing — check syntax, resolve table/column names 2. Translation — convert to an internal relational-algebra tree 3. Optimization — choose the cheapest execution plan (join order, index use) 4. Execution — run the chosen plan, stream results back

The query optimizer uses table statistics (row counts, value distributions) to estimate the cost of alternative plans — e.g. whether to use an index scan or a full table scan, and in what order to join multiple tables. Tools like EXPLAIN (MySQL/PostgreSQL) or EXPLAIN PLAN (Oracle) reveal the chosen plan.

54CORE

Distributed Databases & CAP Theorem

A distributed database spreads data across multiple physical nodes for scale and fault tolerance. The CAP theorem states a distributed system can only fully guarantee two of the following three at once, in the presence of a network partition:

PropertyMeaning
Consistency (C)Every read sees the latest write
Availability (A)Every request gets a (non-error) response
Partition tolerance (P)The system keeps working despite network failures between nodes
Since network partitions are unavoidable in practice, real systems choose between CP (consistent but may reject requests during a partition) and AP (available but may serve stale data).
55CORE

Sharding & Replication

Sharding (horizontal partitioning): splitting one large table's rows across multiple database servers by a shard key (e.g. customer region), so each server holds only a slice of the data.
